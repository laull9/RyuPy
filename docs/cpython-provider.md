## 1. 产品边界与保留资产

RyuPy 继续将应用编译为 .NET CIL，并用 NativeAOT 生成可分发入口；CPython 成为标准库
和第三方扩展的通用兼容 provider。复用其导入器、对象模型和原生扩展机制，减少逐库适配。
纯 RyuPy 模式继续保留：适合闭包已支持的应用、轻量包和编译性能实验。

保留现有前端、中端、CIL 发射、模块计划、资源部署、C ABI、原生标准库和测试证据。
现有联合应用见 `tests/aot/stdlib_service/`，其 README 记录了 macOS arm64 的七步验收；
CPython provider 的同程序迁移独立建立结果；原业务源码与资源保留。

## 2. 目标分层

```text
Rust driver：模块/provider 选择、依赖闭包、目标 ABI、分发计划
    │
现有 syntax → hir → ty → mir → codegen-cil → 编译后的应用
                                                 │
                                      RyuPy.Runtime 对象协议
                                         │              │
                                 原生语义/typed 快路   CPython 对象代理
                                                        │
                              RyuPy.CPython（计划中的 C# 组件）
                                      │ 静态互操作 / 回调
                              最小 C shim + 随包 libpython
                                      │
                              标准库、扩展、包数据、原生依赖
```

- Rust 编译器不在编译进程中载入用户扩展；driver 读取声明和收集依赖，动态探测须单独标记。
- HIR / ty / MIR 保留 Python 通用语义；必要的跨域操作显式进入 MIR / RuntimeFn。
- codegen 只依赖 MIR 发射声明，禁止读取 HIR、扫描包或决定 provider。
- Runtime 定义中性的 provider 与对象操作合同；互操作组件依赖该合同，入口负责组合与注册。
  Runtime 不反向依赖互操作组件；先以独立命名空间/项目隔离，只有真实复用需求才提取合同程序集。
- `PyObject*`、引用计数、GIL 和 C API 只出现在互操作组件 / shim，通用快路不散布这些判断。
- 新互操作项目、ABI 和构建声明按下述竖切接入，遵守同一分层合同。

## 3. Provider 与导入域

构建期冻结每个完整模块名的 provider：RyuPy 编译源码、现有原生运行时或 CPython。
记录选择理由、版本、RID、CPython ABI、资源与原生依赖边；运行中固定归属。
CPython 的普通源码依赖直接交由其导入器执行，无需让 RyuPy 编译器支持依赖内部全部语法。
应用中尚未支持的语法仍报 Diagnostic；未来整模块委派须显式声明和单独验收。

CPython 拥有该域唯一的 `sys.modules`，RyuPy 持有指向同一模块的代理。重复导入、
包属性、类型和异常身份必须稳定。一个完整模块名只能有一个初始化权威，禁止双份执行。
CPython 反向导入编译模块时，通过预注册的模块代理和静态回调访问同一 RyuPy 状态；
跨域循环导入遵守半初始化模块状态，失败按原语义回滚，不在两个缓存中复制业务状态。

首个联合应用中 `urllib`、`base64`、`gzip`、`json`、`sqlite3`、`importlib.resources`
及其内部依赖统一归 CPython。`sys.argv` 与包 `appdata` 的归属在计划里明确：argv 同源，
资源包交给 CPython 导入器并随包部署；编译应用通过桥读取对象。
共享类型、模块全局状态或 C 扩展状态的依赖组整体选 provider，禁止逐 API 随机混用。

首次完成 CP1–CP3 之前只提供显式试点；之后再验收默认兼容配置切换和原生模式回归。
不隐式搜索系统 Python、不因加载失败更换解释器，也不把整个应用悄悄交回解释器。

## 4. 宿主与可搬迁分发

### 4.1 初始化合同

- 固定 CPython 3.12.13、常规 GIL、单主解释器、每进程一次初始化。子解释器、free-threaded
  和反复卸载重载留到独立里程碑，宿主状态机先拒绝这些组合。
- shim 以目标 CPython 头文件编译并封装 `PyConfig` / `PyStatus`，托管侧不复制 C 结构布局。
  使用隔离初始化，明确 `home`、搜索路径、argv、编码、site 策略与字节码缓存位置。
- 路径由可执行文件所在分发根解析，忽略外部 `PYTHONHOME` / `PYTHONPATH` 和用户 site。
  隔离配置控制依赖来源；它不提供恶意 Python 的安全沙箱。
- 初始化失败在可恢复边界返回带阶段、路径、ABI 和原因的诊断；错误发生在解释器可用前时
  由宿主输出稳定错误，不强行构造 Python 异常。普通文件不新增 hash 验收流程。

### 4.2 分发内容与来源

完整基础发行优先于激进裁剪：携带 libpython、shim、标准库源码/必要启动模块、平台扩展
（含 `_sqlite3`、`zlib`、网络所需组件）、选定第三方包、dist-info、包资源、原生依赖及许可证。
首轮保留标准库文件布局；压缩、去源码与细粒度裁剪后置。动态导入使用声明清单和收集理由。
Linux 的共享库及加载器搜索路径、macOS 的 install name/rpath 与签名、Windows 的 DLL
搜索目录与 runtime 依赖分别验收；system-library 白名单按平台维护。

发行来源在 CP1 冻结：选择可再分发且可重建的 CPython 构建，记录上游来源、版本、构建配置、
许可证和系统依赖。不得直接复制开发机 venv 当作产品。NumPy wheel 需匹配 Python、ABI、
平台与架构，连同其携带的 BLAS 等库一起收集。证书/CA 来源和离线安装策略写入分发清单。

沿用 `.build/` 与 `.dist/`，先生成候选目录再发布，失败保留上一份可用 dist。
JIT 也使用同一依赖计划，只允许明确的开发环境覆盖；开发环境覆盖结果单独标记。

### 4.3 线程与关闭合同

每次跨域调用都有解释器租约和 GIL / thread-state 管理；允许同线程重入，受控登记外部线程。
取得 GIL 前不得持有会被 Python 回调再次获取的托管锁。C# 异常在回调边界转换为 Python
异常，禁止托管异常越过 C 栈。异步回调仅在显式注册、保活和注销合同下进入。

关闭顺序：禁止新的外部租约 → 停止并等待外部调用/回调 → 执行应用显式清理 →
在解释器存活且持有 GIL 时排空可释放引用 → 在初始化所属线程完成解释器终止 → 退出进程。
Python 退出钩子由解释器终止流程执行，宿主不得预先重复执行。终止期间仍被 Python 持有的
托管代理与回调根保持有效；仅允许清理线程的受控重入，禁止启动新任务或等待新的外部回调。
终止完成后统一清除剩余托管注册。关闭中出现死锁、重入失败或未清注册时验收失败。
原生扩展共享库保留到进程结束，禁止仍有对象或回调时主动卸载。
CLR finalizer 不直接调用 CPython；释放进入宿主队列，在合法线程执行。
关闭后收到迟到释放只做托管登记清理，禁止重新进入解释器；泄漏计数须可观察。

## 5. 通用对象桥：兼容性合同

### 5.1 值、身份与别名

CPython 对象以受控持有句柄表达，统一定义 new / borrowed / stolen 引用转换。
borrowed 引用离开借用作用域前必须提升；stolen 的成功与失败路径均明确责任。
所有获取、转移和释放带解释器标识，禁止跨解释器或关闭后使用。

按执行域与对象地址维护代理身份及反向映射；缓存使用弱代理关系，防止缓存自己成为根。
同一对象往返保持 `is`、类型与可观察别名。str/bytes/int 等值转换也要区分按值读取和
对象传递：只在不可观察身份或显式数据转换处复制。可变 list/dict/set 和任意用户对象
使用代理；禁止默认递归复制或 JSON 序列化。元组中的共享对象仍保留引用。

实现的公共协议首先覆盖属性读取/写入、位置/关键字调用、迭代、下标、长度、真值、比较、
上下文管理和异常；精确 Python 对象传给扩展时直接使用其真实对象。RyuPy 对象反向暴露
采用通用 Python 代理类型；扩展要求精确内建布局时，实施明确的物化/写回合同或报类型错误。
当前试点提供显式 `container_transfer="synchronized"`：精确list/dict在跨域调用边界物化并
写回，保留共享引用、环、回调重入和异常前副作用；默认 `proxy` 使用活代理。
同步模式当前暂缓两域后台线程并发修改同一容器。ndarray始终持有真实Python对象。
“通用”指共享机制，验收按具体协议和对象类型列覆盖表。

协议清单还要登记算术/反向算术、哈希、字符串表示、类型查询与异常匹配；涉及哪个操作，
就从 MIR 到桥接测试贯通该操作。CP1b 交付联合应用和 NumPy 所需的共享协议，后续补齐
由实际应用驱动。禁止新增按包名分支的专用对象桥，也禁止将缺失操作静默换成托管值复制。

### 5.2 回调、异常与跨堆循环

RyuPy callable 通过静态 thunk 和稳定注册句柄暴露为 Python callable，CPython 持有期间
托管根保持有效。Python callable 传回 RyuPy 复用原句柄。回调抛错必须恢复原异常类型、
实例、消息、cause/context 与 traceback 链，混合栈显式标记；不能统一压成字符串错误。
RyuPy 的 `except` 匹配跨域异常身份/继承链，异常对象本身参与生命周期管理。

跨堆引用图是独立验收项：CPython→托管回调→Python 对象形成的环，两边 GC 都无法仅凭
各自视图可靠回收。首轮为应用生命周期内的隐式跨堆环采用宿主登记及显式断环作用域，
正常释放与关机须清空注册；文档公开自动回收的边界。长期持有回调提供注销合同，并进行
重复创建/释放的稳态测试。若真实 NumPy 用例产生无法管理的隐式环，CP3 阻塞，先补联合
追踪设计；禁止用重复 GC、进程退出或空 finalizer 冒充生命周期门通过。

### 5.3 Buffer 与后续性能

首轮 ndarray 不转成托管 list：使用 opaque Python 对象调用 NumPy，保证 ndarray/dtype/
view 的真实行为。需要托管消费时先提供显式复制合同；零拷贝留作独立可选能力。
后续 buffer lease 必须记录 dtype、shape、strides、只读/可写、连续性、owner、pinning
和释放线程；所有借用覆盖完整调用期，避免悬空内存和隐式写回。

## 7. 长期 AOT 与性能路线

CP4：完善传递依赖、动态导入声明、资源/metadata、诊断与三平台 standalone；按固定应用
逐步扩大标准库覆盖，再做 onefile 解包/缓存/退出清理、签名与可重复构建。
以相同源程序、依赖版本和输入对照 CPython 与固定版本 Nuitka，记录正确性、安装前提、
包大小、启动、吞吐、峰值内存和构建时间；明确 Nuitka 配置与 RyuPy 执行域。

CP5：先收集跨域次数、GIL 等待、代理/句柄分配、复制字节数及原生计算占比。
优先减少跨桥往返、缓存带失效条件的调用目标、批量数据处理、局部特化及 buffer 借用。
性能热区保持纯 typed CIL，守卫失败回到同一语义合同的通用路径，回退不得重复副作用。
只对实测热点设计 C# 替换；执行域内状态与类型相容性要一起验证，不能按单函数速度换掉
共享全局状态模块。每次替换同时运行无优化/优化、JIT/AOT 与应用级差分及性能对照。

默认优化晋升前冻结测量方法、噪声阈值和回归预算；收益必须来自端到端重复采样，
包含启动、内存、包体积与维护成本。更好性能是工程目标，证据随具体 workload 发布。
