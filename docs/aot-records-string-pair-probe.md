# records 字符串对探针实验

状态：基于 dev `81758bb4` 的独立候选，只建立运行时基础和测试合同。
**未接入 MIR，默认 records 仍构造原 tuple；没有产品加速或完整验收结论。**

## 本切片

`PyDict.StringPairAccess` 是显式创建的独立访问器，不给每个普通字典增加字段。
它在默认比较器和全表精确二字符串 tuple 键域成立时，使用 .NET alternate lookup，
探针为只保存两个 string 引用的值类型。原索引、槽位、值与插入顺序仍是唯一存储。
命中读取/覆盖不分配 tuple，真正插入交给原 Set 并物化真实 tuple。

缓存仅保存域证明，不保存值或槽位。访问器自己的安全插入承接插入后的版本证明：
既有键和新键都已证明为精确字符串对，无hash/eq用户回调；不再为第N个新键扫描前N个键。
外部结构版本变化仍使证明失效，并且仅在槽位总数（含墓碑）不超过256时重新扫描。
超过预算立即拒绝，且同一版本持续拒绝；不是只拒绝一次，也不因普通值覆盖恢复快路。
后续clear或缩小并整理到预算内，可以重新扫描建立证明。连续外部修改最多每次检查256槽，
因此不会退化为随表规模增长的全表二次扫描；大表的正常访问器自身增长不受256键限制。
非字符串成员、tuple 派生及自定义比较器全部拒绝；拒绝发生在 hash/eq 和写入之前。
调用者必须沿原 tuple 路径继续，不能将拒绝解释成缺键。异构键删除后仅在扫描预算内
重新证明域。这里的外部任意修改指Python允许的字典操作；没有绕过版本守卫的别名写入许可。
原 tuple 的 `Items` 被 CLR 宿主直接篡改不在 Python 不可变 tuple 合同内；不能据此声称
外部任意 CLR 反射写入后缓存有效。Python 可见别名、字典顺序和键对象身份不改变。

## 尚未实现的编译器合同

原始 records 的 `key` 是具名局部，横跨 `get`、加法与写入。
不能直接扩大 tuple_scalar：`locals()`、用户 `__add__` 或 hash/eq 回调可观察真实 tuple。
下一切片需建立显式物化映射并证明区域无观察；入口守卫包括字典精确类型、当前键域、
两个精确字符串，以及会被消除动态算术的精确数值证明。所有源实参在原位置冻结。
守卫失败使用同一原 tuple，不重放已发生副作用。区域内产生异常必须保留源码行号。
未知用户调用、反射观察、暂停和不可证别名都是退出边界，不按函数名匹配 records。

固定布局读取/方法正文专门化是另一切片。当前 PyInstance 已经是类槽位加 object[]，
必须复用其存储并守卫类版本、描述符与实例遮蔽，不另造并行 Record 对象表示。
