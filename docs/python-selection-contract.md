# Python 版本选择：P0 纯合同

本阶段只有 `ryupy-driver::python_selection` 的内存决策与合成测试，尚未接入 CLI、
provider、宿主或 shim，不改变现有 CPython 3.12.13 的产品要求，不代表已支持3.9运行。
目标是构建期选择与冻结3.9及以上发行，运行时不寻找系统 Python、不下载、不换版本。

## 边界与数据流

后续执行层收集候选事实 → 完整 PEP 440 解析器转换项目约束 → 本模块选择 →
现有 provider 消费冻结 Binding。模块自身无文件/网络/进程 IO，也不读取环境变量。
当前只接受三段正式版本及已解析约束 AST；不接受原始 `requires-python` 字符串，
不冒充完整 PEP 440 parser。预发行、post/dev/local 等不能被上层剥离后缀再送入。
解析器遇到无法忠实转换的约束必须明确拒绝。~=3.9.0 可展开 >=3.9.0 且 <3.10.0；
!=3.10.* 使用 ExcludeMinor。历史3.12.13 oracle继续独立保留。

Request是独立的内存合同schema 1，并非既有 `ryupy-cpython.json` 的新格式；不提供
序列化承诺。生产接入先与正在开发的provider接口对齐，避免重复发行/包扫描系统。

## 选择规则

1. 始终过滤实现、正式版本、最低3.9、目标平台/CPU/系统ABI、GIL、debug、完整基础发行、
   共享库、头文件、许可证、来源、依赖ABI和支持登记。版本号不是ABI兼容证据。
2. 显式发行/解释器/版本优先于项目pin；`requires-python` 始终是硬约束。
3. 没有明确update_lock时必须复用全部Binding身份相符的锁；失效、缺失、冲突均报
   LockNeedsUpdate，不静默更换。锁含精确版本、发行、目标、SOABI、shim、布局、来源与依赖集。
4. 无显式选择时应用项目单值版本pin。项目环境优先于受管缓存，缓存优先于受管远端目录。
5. 同一来源层选择最高正式版本；同版本多个发行无明确来源策略则报歧义，不按名字随机选。
6. 下载默认禁用。允许时返回needs_download计划，绝不表示资产已经存在或下载成功。

一个发行可以由多个来源或解释器别名发现：不可变事实相同则合并筛选，事实冲突报错。
只有显式请求可以使用Explicit来源。诊断返回稳定排序的候选ID及全部拒绝原因。

## 支持状态不等于版本范围

Unsupported无适配器，不能因“3.9+”自动放行未来minor。Implemented表示有适配器但待验收，
必须显式选择并启用实验；Verified必须是精确发行/版本/平台/构建与依赖组合的真实验收记录。
测试中的Verified只是一项合成输入，不构成任何真实运行证据；未知patch不能继承已验收状态。
当前Support/Facts是可信执行层的声明，不是安全校验机制，后续不得从用户配置直接相信它们。

## 后续探测与生产接入

- 显式解释器必须是可信来源且经用户选择的解释器，不能执行来源不明的项目脚本或包装器。
  仅以隔离子进程运行固定的最小标准库探测代码，使用 `-I -S`、仓库外cwd、清理环境、
  严格超时、输出上限、退出码及JSON schema验证。不能import项目包、执行sitecustomize，
  也不能把“不加载项目代码”等同于恶意解释器安全沙箱。
- venv只作项目选择/依赖线索；须解析对应可再分发基础发行，不直接复制整个venv。
- 交叉构建只读取可信目标发行元数据；不能运行目标解释器，也不能用宿主sysconfig冒充目标。
- ABI适配应由每minor匹配的shim及真实扩展门证明；不得移除现有版本检查绕过缺失API。
- 生产接入保留失败事务、许可/来源、路径封闭、依赖闭包、搬迁及干净机验证。
- 单元测试后仍须真实driver编译、完整集成回归及每目标CP/JIT/AOT验证，才能宣称产品支持。

## 验证方式

正常集成后执行 `cargo test -p ryupy-driver python_selection` 与项目完整检查。
资源受限且现有集成门并发时，可在仓库外建立无依赖Cargo harness，将lib.path指向
`python_selection.rs`，运行全部内存测试和 `cargo clippy --all-targets -- -D warnings`。
这只验证新模块，不能代替真实driver或产品验证。所有构建/临时产物放仓库外，不提交报告或快照。
