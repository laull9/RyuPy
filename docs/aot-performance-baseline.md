## 1. 概述与基准架构二轮修复

用户授权全面优化 NativeAOT，目标逐项速度不弱于 CPython、峰值内存不高于 CPython，速度优先。
第一轮初测中存在测量缺陷与错误归因。以下为子代理第二轮结果；主代理另发现旧 CLI 复用、统计轮失败漏检及比较协议缺失并修复，正在以冻结原产物复验。

### 1.1 第一轮重大缺陷复盘与纠正

1. **NumPy 失败进程误判为有效性能（致命错误纠正）**：
   - **第一轮错误**：上一轮手写 `subprocess.Popen` 时忽略了 `returncode` 并吞噬双流，固定 CPython 3.12.13 运行 `tests/e2e/phase4/m4_1_numpy_objects.py` 实际上以退出码 1 抛出 `ModuleNotFoundError: No module named 'numpy'`，上一轮误将报错退出的 8.9 ms 当作 CPython 真实性能，进而推导出虚假的「150ms 初始化固定开销根因」。
   - **本轮纠正**：删除所有虚假有效性能和 150ms 假推测，记录完整失败证据；接入与包内锁定的固定版本 `numpy==2.3.5`（`$HOME/.cache/ryupy/cpython-provider/numpy-2.3.5-cp312-osx-arm64`），严格断言退出码为 0 与双流输出。
2. **后台负载干扰独占测量**：
   - **第一轮错误**：在 26 项全量基准后台运行时并发测量 Onefile，测量存在干扰风险；两次载荷与执行域也须核对，不能把 1271 ms 与后续 422 ms 的差异全部归因于竞争。原 26 项数字标注为「第一轮初测（dirty + instrumented + harness）」，不作最终基线。
   - **本轮纠正**：任何重负载前后严格串行，所有测试在无竞争环境下独占运行。
3. **临时工作区与清理边界安全**：
   - **第一轮缺陷**：共享 `temp/ryupy-bench-work` 且在 `finally` 中无条件 `rmtree`，导致并发 runner 互相删除工作区；且 `tempfile.gettempdir()` 可能误配在 repo 内。
   - **本轮纠正**：每次入口由 `TemporaryDirectory` 分配本次唯一独占目录，贯穿 build/profile；强制检查 `gettempdir()` 绝不落在 repo 内；清理仅限于本轮独占根；结果保存使用明确的外部路径并显式打印，不静默覆盖跨 run `latest`，默认运行不永久遗留机器产物。
4. **原生入口识别边界防护与 ADR-0182 免哈希**：
   - **第一轮缺陷**：`artifact.py` 从日志接受任意 root 外文件且 resolve 软链接，回退时混淆 standalone 与 onefile；`host_rid` 错误包含 Windows（但 runner 依赖 POSIX `os.wait4`）；测试中依赖 `manifest_fixture` 计算 SHA256。
   - **本轮纠正**：严格限定只接受本次独占 root 内、匹配预期 mode 的真实普通文件（拒绝符号链接与逃逸）；回退至 POSIX（Linux x64 与 macOS arm64）边界；依 ADR-0182 跳过所有普通文件 SHA 计算，改用手写平台二进制头（Mach-O / ELF）与权限核验。
5. **主表采样公平性与双流校验**：
   - **第一轮缺陷**：直接脚本只采 1 个样本却当作中位数；主表混入了 CPython 外壳（harness 带来额外 ~6ms 导入）与 RyuPy 的 `RYUPY_STATS` 统计注入；统计 JSON 损坏被吞空。
   - **本轮纠正**：主表采用 **纯净直接脚本 CPython vs 原生 RyuPy**（双方均无外壳、无统计环境变量注入），严格执行 1 次热身 + 5 次计时（1warm5）交替采样；独立 instrumented 轮单独收集 `MarkMainStart`、分配量、GC 次数与暂停耗时；严格校验退出码为 0，捕获完整 stderr。
6. **模式防混淆与 Smoke 阻断**：
   - 公开 `--native` CLI 开关并在报告中隔离记录；在结果比对时拦截跨 backend 与跨 native 模式的比对；AOT 下前置 hello smoke 基础设施自检，遇到编译/验证/运行致命失败立即阻断。

## 3. 联合应用与扩展（NumPy 专项实测与失败证据）

针对用例 `tests/e2e/phase4/m4_1_numpy_objects.py`（数组构造、切片视图原地修改、广播运算与越界异常传播）：

### 3.1 第一轮失败证据保留与勘误

- **第一轮错误回放**：第一轮在未提供任何依赖环境变量的情况下，手写 `subprocess.Popen` 执行固定 CPython 3.12.13，未检查 `returncode` 并吞噬 stderr；实际上该进程以退出码 1 抛出：
  ```text
  Traceback (most recent call last):
    File "tests/e2e/phase4/m4_1_numpy_objects.py", line 3, in <module>
      import numpy as np
  ModuleNotFoundError: No module named 'numpy'
  ```
  耗时 ~27 ms（上一轮测到 8.9 ms）完全是 Python 解释器启动并报错退出的耗时！上一轮将报错退出时间记录为有效性能并妄断出「150ms 初始化固定开销」，系重大失实。

### 3.2 第二轮严格环境复测

本轮采用严格的退出码检查、完整 stderr 捕获与双流逐字节校验：
1. **CPython 3.12.13 + 包内锁定版本 `numpy==2.3.5`**：
   - 依赖来源：`$HOME/.cache/ryupy/cpython-provider/numpy-2.3.5-cp312-osx-arm64`（由 `tests/cpython/prepare.py` 锁定的包内一致版本，不篡改系统 Python）。
   - 退出码：`0`（正常退出，无 stderr 报错）。
   - 输出断言：完全通过（包含视图切片别名修改 `[[10, 3], [4, 5]]` 与 shape/index 异常）。
   - **1warm5 墙钟中位数**：**32.4 ms**（各次：32.1, 32.4, 32.2, 32.5, 32.5 ms）。
   - **峰值 RSS 中位数**：**26.73 MiB**。
2. **RyuPy 纯 NativeAOT（`--native`）现状**：
   - 在纯 NativeAOT 模式下编译生成二进制，直接执行时抛出 `ModuleNotFoundError: No module named 'numpy'`（退出码 1）。
   - **结论**：第三方 C 扩展与 NumPy 对象桥属于 CPython Provider 范畴（须通过 `--cpython-provider` 声明分发载荷），在纯 NativeAOT 编译域下尚无内置实现，因此纯 NativeAOT 下对第三方 C 扩展的性能对比明确标记为**未完成/不适用**，绝不以失败数据伪造基线。

## 5. 瓶颈诊断与错误归因纠正

针对速度落后项与峰值内存超标项，纠正第一轮中的推测性错误归因：

### 5.1 诊断错误纠正

1. **`containers` 内存与分配瓶颈纠正**：
   - *第一轮错误*：将 2.4GB 分配量完全归因于列表/字典的“数值装箱与频繁扩容”。
   - *事实与纠正*：检查 `tests/benchmarks/containers.py`，源码中除了 20 万次 `items.append(i)` 和 10 万次 `lookup[i]` 读写外，**明确包含 5 万次 `text = text + "b"` 字符串拼接**！5 万次字符串累加产生了海量的新字符串对象与连续大对象堆（LOH）触发。因此 `containers` 的分配是**字符串拼接累加与容器装箱的复合瓶颈**，不能全归装箱。
2. **`generators` 生成器根因纠正**：
   - *第一轮错误*：推测“生成器每次 yield/next 依赖状态机显式将变量溢出到 object[] frame，每次暂停/恢复 new frame”。
   - *事实与纠正*：生成器实例在其生命周期内是由同一状态机推进，**frame 不是每次 new**；高频迭代的实际分配点、存活引用和 GC 暂停归因仍需剖析，不能从总量直接推断原因。
3. **`oop` 多态分发纠正**：
   - *第一轮错误*：声称“4 子类超出 PIC 容量的多态分发”。
   - *事实与纠正*：在 `tests/benchmarks/oop.py` 中，4 个子类（`Square`, `Rect`, `Tri`, `Line`）在 PIC 容量为 4 时**刚好容纳，不必抖动**。实测 RyuPy 耗时 83.1 ms vs CPython 81.2 ms（加速比 0.98x），多态分发性能基本持平。

### 5.2 核心优化瓶颈排序

1. **P0（字符串累加 `+=` 与就地缓冲）**：
   - `str_concat` 慢 5.9x（1008 ms vs 174 ms），分配量高达 19.1 GB，RSS 达 157.6 MiB；
   - 解决 `text += char` 路径的缓冲区重用是消除最大性能与内存差距的决定性入口。
2. **P1（推导式扁平化）**：
   - `comprehensions` 慢 3.3x（152 ms vs 46.1 ms），GC 暂停高达 52.9 ms；
   - 先确认实际环境分配与迭代器路径，再评估保持作用域的无逃逸推导式循环展开。
3. **P2（容器数值直接类型化存储与装箱消除）**：
   - `containers` 慢 4.5x（154 ms vs 34.4 ms），`sieve` 慢 2.3x（171 ms vs 75.1 ms）；
   - 先单独消除字符串累加成本，再评估布尔/数值容器表示，保持元素身份和异构写入。
4. **P3（生成器状态机与迭代吞吐）**：
   - `generators` 慢 3.5x（420 ms vs 119 ms），GC 暂停 46.4 ms；
   - 优化生成器状态机字段访问与生成器表达式求和内联。
