# ADR-0036：非 SSA 上的有限值域证明与自动拆箱

状态：实现、正确性门禁与专项/整套配对已验证；接受有限规则默认启用，不承诺整套程序净提速。

## 按 ADR-0002 重新评估表示

已有精确装箱类型 must 分析通过写入 kill、合流交集与固定点处理守卫拆箱。
它不从 Python 注解或 isinstance 推导精确 long，因此不会把 bool 子类型当作 long。
直接累加与叶调用实验进一步表明：生成更多守卫不自动带来全路径净收益。
本切选择可在编译期完整证明的窄机会，而不是再增加一套运行时猜测状态。

考虑三种方向：严格 SSA 需要重建局部定义、phi 和 CIL 前消解；只读 SSA 视图
仍需要支配/phi 索引及与原 MIR 写入的映射；当前有限闭区间只需前向工作队列。
因此首批验证继续非 SSA 数据流，不为两个局部数值范围的合流先改整个构建器。
这不是否定未来 SSA 价值；更广循环归纳、逃逸/特化需求应再按收益评估。

## 事实与收敛

仅记录 i64 闭区间或未知 Top，未访问基本块与已经可达但无事实严格区分。
Box<I64>、局部 Use、精确拆箱以及已证明不溢出的原生 Add/Sub 可传播范围；
未知调用返回、普通动态运算、bool 装箱、全局或 cell 读取均不猜测范围。
不利用可执行用户比较的 `0 <= x < 10`，不凭标注拒绝合法 Python 值。

合流为区间凸包；任一路径缺事实则合流未知。写入先读右值再 kill 旧目标。
每个块/局部范围两次扩张后再扩大则提升 Top，之后不凭后到路径恢复更强事实。
同时限制块数、局部数、工作队列处理次数和语句处理总量；预算耗尽整函数不改。
这会保守遗漏多前驱或循环机会，但避免无限收敛和不确定的编译时间。

## 原位改写与语义

分析完整收敛后才收集改写计划，最多三十二个原动态、非 inplace Add。
两个动态操作数必须各有精确 i64 范围，使用 i128 算范围端点并确认完整和区间
落在 i64。原位置改为两次 ExactUnbox、原生 checked Add、结果 Box。
范围不明、可能溢出、bool/float/BigInt/用户对象都保原动态运算，不插类型拒绝。
checked Add 仍作机械防线，但正确性依赖证明，不能用 OverflowError 替代整数升级。

只替换原加法新结果；不折叠原 Box/Use 或更换既有操作数对象。
已有整数盒的别名和身份保留；大于小整数缓存的 `x + 0` 仍生成与 x 不同的新盒。
不传播尚未改写的 DynBinary 结果范围，避免后继计划依赖改写预算之外的操作。
排除 EH、环境、cell、生成器与暂停；不重新执行操作数或移动用户副作用。
后端只看到既有 MIR 原生指令，无新 RuntimeFn、C# 容器或解释器状态。

## 验收与取舍

pending 差分先覆盖两分支常量、bool 混入、未知用户参数、i64 两端溢出、
未绑定局部、增长回边、身份/别名与 EH/暂停回退。
结构测试必须锁真实范围与实际 ExactUnbox 命中，预算耗尽则原 IR 完全相同；
不能让一个未被优化的程序通过差分来证明拆箱正确。

独立基准区分函数调用中的 diamond 与循环内 diamond，保未知/bool/overflow 对照，
按相同 runtime 交错比较、检查真实 JIT 指令与分配，而不是只数 MIR 中少了 dyn.Add。
预期机会是减少装箱上的动态分派；输入盒与结果盒仍可能存在，不能预报零分配。
若 JIT 本已消掉原分派或分析/代码成本无净收益，则不作为默认优化。


## 专项实测与综合取舍

两组同 runtime 配对已归档
`tests/perf/results/m3_9/interval-candidate`，保存完整原输出、每进程分布、
实际汇编、来源补丁和分配。四个已改写场景默认模式两组均改善约 10–48%；
禁 tier 首组 loop_true 慢约 8%，其它已改写场景改善。FullOpts choose 从
697 B 降到 292 B，loop 从 1493 B 降到 1099 B；七场景分配量均未改变。
这符合消除动态分派、而非消除原有盒分配的目标。

未知溢出对照不能略去：默认两组慢约 24% / 10%，禁 tier 慢约 33% / 55%。
该未改写路径没有新增算术或守卫；unknown_loop 原始 CIL 相同，
choose_unknown 仅因前面两个 PIC 消除而站点常量从 3 变 1。数值 Binary
不使用此 site 查缓存，不能编造缓存碰撞解释。补充的禁 tier 真实 caller
与 callee 各自完整 Diffable 汇编 SHA 均相同，栈/指令序列没有新增成本。
默认 Tier1 则存在 PGO 计数和布局差异，不能拿它解释禁 tier 的不利观测。

正式计时没有逐时 GC / 调度 / 实地址记录，且未知溢出场景固定在最后；
原因尚未唯一确定，分配相同也不证明 GC 时点相同。保留全部不利样本，
不称其已被证明只是噪声，不把专项已知场景倍数外推成项目提速。
完整 26 项轮转主比较全部语义通过；排 hello 的 25 项默认 variant 进程 main
几何耗时比为默认层次化 +2.8%、禁 tier -5.3%，其中 closures +64.6%、dict_ops
+24.6% 等不利结果完整保留。它不能唯一归因本 pass，也不能被专项收益掩盖。

最终接受的是有编译期证明、独立已改写场景收益和明确预算的有限规则默认启用，
而不是“所有程序更快”。未改写对照的不利原因仍不确定，未来扩大规则需新证据；
不为取得有利数字继续调参或重复统计。完整冷启动、预热 kernel、分配与实际汇编
见 `tests/perf/results/m3_9/full-suite`，M3.10 继续针对真实热点推进。
