# ADR 0076：函数模块成员与真实调用来源前置

状态：较小 Dynamic-owner 前置方案已完成本地专项与正常完整门禁，尚未公开发布。真实函数模块成员和有限来源可用，不代表 `namedtuple` API、tabulate 全项目或 AOT/性能验收通过。

## 背景与范围

锁定 tabulate 0.9.0 的候选 Linux JIT 单入口在 `collections.namedtuple` 导入处失败，见 compatibility.md 的独立记录。实现通用工厂必须保留真实类和 tuple 协议，不能为固定项目造可导入占位。

`namedtuple` 的默认 `module` 需要真实调用函数来源。固定 CPython 3.12.13 的 `sys._getframemodulename` 读取当前帧函数对象的模块成员，不读取调用时模块全局名字。函数创建时捕获全局 `__name__`，随后函数成员可独立赋值、删除。因此文件名反查或每次读取当前全局槽不能代替真实来源。

本 ADR 单独处理这一前置，不同时登记 namedtuple 载体、完整 frame 内省或所有原生函数元数据支持。

## 语义合同

- `PyFunction` 使用真实模块成员，与普通 `__dict__['__module__']` 分离；赋值保留任意对象身份，删除及重复删除后读取 None。
- 创建捕获应在默认值、非延迟注解求值完成后，装饰器应用前；每次真实定义产生独立函数，不能重置旧 alias 的成员或默认值。
- 调用帧保存实际函数对象，冷读取时取其当前模块成员，不保存模块值快照。读取本身不调用真值、字符串或哈希协议。
- 模块顶层使用每次实际执行创建的内部来源；普通原生 helper 不造虚假 Python 帧。未知最顶来源明确拒绝，不向下猜测祖先。
- 生成器保存源函数引用，暂停后恢复仍观察该函数当前成员；正常终结释放引用，忽略 GeneratorExit 后仍暂停的情况不得提前清除。
- 退栈与 Reset 清除新增强引用，避免静态帧数组保留已退栈闭包。异常位置快照仍只保存原有文件、函数与行号。

`namedtuple` 自身的 `or '__main__'` 是后续 API 的逻辑，不能提前塞入通用 raw 来源读取。函数模块值可以是有用户真值行为的对象。

## 性能与分层

最终类型分类为 Dynamic 的函数携实际函数引用；普通 Static 函数保持原参数/返回 ABI，不依赖新的纯函数证明，也不改变其数值槽。普通 Static 帧来源未知，只有实际查询需要该来源时明确拒绝，不向下猜测；其函数对象的 __module__ 成员仍在定义时真实捕获。ModuleMain 是单独入口，即使分类为 Static，仍保持零参数并登记模块执行来源。

静态 `print` 可以经替换输出流调用原生转发器；若没有中间 Dynamic Python 帧，默认来源查询是本阶段明确限制。已有 leaf-inline 继续依赖原调用点 exact/身份/溢出守卫，只在摘要参数计数中排除隐藏 owner，fallback 仍调用保存的实际 callable。

Dynamic 别名 thunk 传真实 self，直调在参数副作用前冻结实例，实参之后从同一实例读取默认值。C ABI 外部约定和空参模块初始化不增加 Python 隐藏参数。

新增成本包括每函数对象一个成员、部分调用的引用参数与加载、帧引用写入/清理、生成器引用，以及真正 def 分配时机变化。普通调用不要求新增 wrapper 或模块字典查询，但未做性能测量，不能声称零开销。此处也不消除历史 matmul 禁分层回归。

## 分阶段验证计划

1. 运行时真实成员与元数据隔离。
2. 定义时序、fresh identity、thunk/direct/生成器来源接线与 Static 原 ABI 结构回归。
3. 三个真实 CP/JIT 应用与一个结构门；C# 内部验证帧生命周期。公开函数成员差分不是完整 frame 来源端到端证明。
4. 独立完整门禁和备份；后续 namedtuple 实际 API 差分才闭合来源消费者，不在前置阶段冒用其成功结论。

每包先审实际实体再首编译。快照如受影响须逐项审实际语义，不整体接受候选。公开推送、项目再次运行、AOT 和性能组不由本 ADR 自动授权。

## 阶段 3 范围重新收敛

全来源方案的隔离 A 草案达到 65 个文件、约 2781 行新增，包含临时调用 IR、优化后纯函数证明、来源数据流和生成器恢复证明。虽然通过首次编译准入的源码审查，它没有应用到本工作树，也没有编译或运行。重新评估收益与风险后，停止该草案，不以既有投入为理由扩展本切。

改采固定 Dynamic-owner 的阶段性路线，具体接线与测试已独立冻结并完成下述专项：最终类型分类后的 Dynamic 函数携带真实函数对象，直调保持既有调用形态、在实参副作用前冻结对象，默认值和帧来源使用同一对象；模块使用本次执行来源。Static 保持原数值 ABI，不追加纯函数证明体系。生成器沿既有局部槽保存恢复，恢复方法仍使用原 frame 参数约定。

这不是完整来源兼容。未来消费者只查实际顶层 Python 帧；当省略或显式 None 的 namedtuple module 参数需要查询而该帧来源未知时，明确拒绝，不能借用更下层模块名。Static 调用 Dynamic Python 回调时，回调有真实顶层来源；内部 C# 测试使用未知 Static 帧加真实 PyPartial，验证没有新 Python 帧的原生转发仍拒绝；这不是已运行的编译 Python Static→partial 反例，也未统计项目级来源覆盖率。显式任何非 None module（包括空串、0、False）不需要调用者来源，不能按真值误走默认查询。此处是后续 namedtuple 合同边界，不表示其 API 已经实现。

上文优化后 NoCallback/完整 Static-owner 计划是已停止方案，不作为本切待实现承诺。新的较小路线仍需准确的签名、定义成功发布和实例冻结检查，以及直接/别名/生成器/异常测试；不承诺零运行成本或全部普通函数支持。

较小路线增加两项 C# 内部边界测试：真实 PyFunction 回调进入后能读取并实时观察其 Module，正常/异常退出后恢复未知 Static 顶帧；真实 PyPartial 转发至内部 reader 不创建 Python 帧，因此仍明确拒绝且不借用祖先。首次编译在测试的 `throw PrepareRaise(...)` 遇返回类型 object 的 CS0266/CS8619，未运行测试；精确 PyValueError cast 经独立审后重编，2/2 通过、零跳过。未改生产异常处理或公开注册测试 API，手动入口钩子不等于编译 Python 或 namedtuple 端到端成功。

较小编译器方案实际补丁为 60 个文件（31 个生产接点、29 个测试文件，包含构造器字段机械初始化），约 +850/-132 行；不是只有几个文件的小改，但未引入旧 65 文件草案中的临时 IR、优化后 pass 或全 CFG 来源证明。首次专项通过：来源校验 3 项、原叶内联兼容 2 项、运行时 ABI 3 项、后端结构 1 项、真实源码结构 1 项，以及三个固定 CP/JIT 应用 3/3。所有结果为小方案实际接线后的验证，不复用 Stage2 通过冒作新 ABI 已验。结构测试格式化后超过 600 行，经独立审机械拆为主文件与辅助模块；首拆分因一处重复 pub(super) 解析失败，未执行测试，保原日志。只删重复前缀后重编，结构仍 1/1 通过，全部断言保留。当时启动正常完整门禁，后续首失败及最终终态记录如下。
