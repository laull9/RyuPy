# ADR-0172：AOT 分发与完整标准库接入路线

状态：设计提案，等待交叉评审；本文件中的后续能力均需独立实现与验收。

## 目标与当前落点

2026-11-13 用户将 AOT 打包、完整标准库与 C ABI 接入列为重心。近期以可搬迁
standalone 为交付单元：一个应用的编译模块、包数据、原生库同时进入可解释的发布计划。
完整标准库是长期目标，逐 API 和目标平台登记，固定第三方项目集继续衡量实用兼容。

当前代码拥有 C# 底层标准库适配、四模块纯 Python 源码 catalog
（`_markupbase`、`html`、`html.entities`、`html.parser`）、显式资源计划、
固定 `(i32,i32)->i64` C ABI 单库多导出，以及资源/绑定组合发布。
libpython 宿主、版本化全标准库 catalog、通用 ABI 和自动原生依赖闭包仍待实现。

## 决策方向

上层纯 Python 标准库优先复用固定版本源码，经用户源码相同的编译链生成 CIL。
C# 提供对象模型、异常、导入、编码和系统适配；有成熟原生实现的能力通过声明式 C ABI 接入。
保留成熟的现有 C# 模块，按完整模块选择 provider，避免同一模块的类、异常和状态混用。

显式 CPython 兼容模式由独立宿主负责 libpython、扩展初始化、GIL、引用所有权、
对象转换与异常传播。兼容模式必须明确选择并在报告中列出桥接模块。
发布包可携带固定版本 libpython/标准库/扩展，使目标机无需预装 Python；
允许外部环境模式时另列依赖，不默认探测并悄悄回退到解释器。

Native 模式继续生成 RyuPy 原生程序并携带必要资源与非系统原生依赖。
动态 `exec/compile`、开放动态导入等需要单独执行机制；纯构建期源码闭包无法满足其全部行为。
近期在兼容模式承接这类合同，长期原生动态执行方案另立 ADR，完整目标持续登记未完成项。

## 归属与计划数据

- driver 管理模块 provider、源码版本、依赖边、收集理由、数据文件、原生库及传递依赖、
  许可证、目标平台和部署路径。沿现有 ResourcePlan/绑定计划扩展为统一分发计划，逐步迁移。
- HIR/ty/MIR 补通用 Python 语义与显式 RuntimeFn；不按标准库模块名绕过语义。
- CIL 后端只消费 MIR 与明确发射输入；扫描源码、选 provider、查找库和资源均留在 driver。
- runtime 承担对象和协议；CPython 宿主与原生 runtime 边界独立，禁止把 PyObject 生命周期混入通用对象快路。

同次发布先校验并冻结全部输入，生成完整候选目录，再安装 dist。报告记录真实来源、
收集理由与已知缺口；已存在的清单校验沿原合同执行，不额外增加普通文件 hash 验收步骤。
来源不明的动态依赖应明确失败或要求显式声明。

## 实施顺序与验收

1. **组合交付**：资源、as_file 与两个 C 符号在同一程序运行；v1/v2 声明兼容，
   失败保留旧 dist，源码/原库/构建目录不可用、换 cwd 后运行正确。
2. **版本化标准库 catalog**：以项目固定 CPython 版本为准，列目标平台的公开模块/API、
   内部依赖、源码许可证与版本；沿已支持依赖闭包扩展，逐模块选择 provider，
   缺语义先补通用机制。上游测试与 CP 差分共同决定 API 状态。
3. **扩展 C ABI**：先 buffer/长度、opaque handle/销毁与错误合同，保持构建期静态发射；
   再多库和传递依赖收集。用 zlib 或 SQLite 的真实操作验生命周期和搬迁，
   每个原生库单独处理版本、许可证、系统依赖白名单及平台 ABI。
4. **兼容宿主**：建立显式 libpython 分发与 CPython 扩展桥接，验证对象往返、回调、
   GIL、错误和释放；固定第三方项目的桥接结果单独登记。
5. **收敛完整标准库**：按公开 API、动态执行与平台模块逐项关闭缺口；
   standalone 稳定后再处理 onefile 解包、缓存、资源生命周期与诊断。

新增组合能力先在 macOS arm64 验收，再在 Linux x64/Windows x64 实机和免装 SDK/runtime
目标环境验收。宿主搬迁、干净目标机、平台和项目通过各有独立证据，不复用未执行的结论。
