# ADR-0208：全 CIL 执行与 libpython 底层化

- 日期：2026-11-16
- 状态：方向已接受；实现与验收待启动
- 决策来源：用户要求所有 Python 代码进入 CIL，libpython 仅做底层库提供，移除 Python 胶水；本轮写入规划
- 接续：ADR-0181 的长期执行归属方向；宿主、对象 ABI、分发和已有验收资产保留

## 背景

ADR-0181 的 provider 路线以及 ADR-0204–0207 已打通真实项目与分发，但当前依赖
源码委派、Python 辅助函数、标准库解释执行和随包源码数据。用户确定下一阶段收回
Python 执行归属，以便统一语义、跨模块优化、调试与交付。

## 决定

1. 应用、纯 Python 标准库和第三方 Python 函数体全部编译为 CIL；libpython 保留
   对象 ABI、引用/内存管理、异常及原生扩展需要的底层能力。原生库继续使用机器码。
2. 内部导入、类构建、描述符和回调包装迁移到 CIL 与必要的静态 C shim，移除嵌入
   Python helper。函数、类和反射优先采用运行时数据与预编译操作函数。
3. 异步在中端生成显式状态机；反射由编译元数据、对象协议及帧模型提供。
   .NET Task 承接底层等待，Python 调度与取消语义由 RyuPy 负责。
4. NativeAOT 以构建期代码生成为主；任意运行期新增代码的 JIT 能力单独规划，
   缺口给出诊断，严格候选域内禁止自动回落 CPython 执行。
5. 最终门覆盖产品启动、运行和关闭，要求零 Python 源码胶水及零 CPython 字节码执行。
   libpython 的 frozen 启动模块也进入 C0 盘点；仍使用该执行链的产物处于过渡阶段。
6. 阶段顺序为 C0 盘点、C1 内部胶水、C2 对象/反射、C3 异步、C4 完整 Python
   闭包及底层内核、C5 默认晋升与退出。详细合同见[实施路线](../cil-execution-roadmap.md)。

## 迁移与代价

现有兼容模式维持独立基线。先显式验证候选路径，通过同次 CPython、原项目、
JIT/NativeAOT、删除输入搬迁、平台和性能门后才逐步晋升。切换默认和删除旧代码
分别交付。当前模式、既有项目成绩和未完成边界保持原记录。

主要成本集中在动态对象协议、反射/frame/code 可观察行为、异步取消与资源清理、
C 扩展对精确 CPython 对象布局的假设，以及启动内核维护。逐 API/消费者验收这些边界，
候选域出现新增失败即停止该切片晋升。最终无源码产品对原文查询给出明确异常，
可选外置调试源码独立管理；资源与持久用户数据不再依赖随包 `.py` 文件充当锚点。

libpython 底层化与完全移除 libpython 分别登记。字节码执行归零后，GIL、引用计数和
原生依赖合同仍按保留的底层能力维护。性能、启动与体积收益以实测发布。
