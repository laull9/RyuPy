# ADR-0033：以受守卫的 CIL 局部状态替代累加器包装

状态：已作性能决策——保留 holder 默认路径，直接局部方案显式实验、默认关闭。
三组方案的正确性与性能证据、显式模式接线和本竖切聚合门禁均通过；不代表 M3.9 完成。

## 背景与证据

用户要求让生成代码尽量命中 .NET JIT，而不是在 C# 底座再造解释器。
M3.6 的累加器包装已经消除受支持循环的逐轮整数盒，但每次函数仍创建 holder。
M3.7 发布版 `e1c1ee1` 的实际机器码显示：Tier0 保留公开 Add 调用，
Tier1-OSR / 禁 tier FullOpts 已内联公开包装，仍存在 holder 状态操作。
因此本实验不能以“首次消除稳态 helper 调用”为收益理由。

基线负载为 `tests/perf/dataclass_hot.py`，固定 .NET SDK 10.0.403 / CoreCLR 10.0.14。
独立分配诊断中，五次字段循环调用共一百万轮分配 360 B，包含固定诊断与结果开销；
没有逐轮分配不等于函数零分配。后续使用保存的产物与候选交错配对重测，
不能将不同时段单边最佳结果相除。默认 tier、禁 tier、Tier0 / OSR / FullOpts 分开报告。

## 有界方案

保留原候选限制：入口 preheader 无前驱，单 header / body / latch / exit，出口无旁路；
无 EH、生成器、环境或 cell。循环内累加局部只能参与末尾唯一的 inplace 加法，
不得在 RHS、别名、调用参数或其它观察中出现。每函数最多一处，不以基准函数名匹配。

MIR 保留原动态对象槽，增加 i64 值、精确整数标志和 dirty 标志。
初值保留原对象；RHS 在原位置求值一次后冻结。
仅双方实际为 boxed System.Int64 时执行 wrapping add，按符号位判断溢出。
成功只更新 i64 与 dirty；溢出、bool、浮点、用户对象均进入完整原动态 inplace 协议。
慢路先物化旧整数值，运算成功后才更新状态，不能把溢出的 wrapping 结果当旧值。
出口仅 dirty 时物化一次，保持零轮初值身份、用户方法返回的已有整数盒及最终多次观察身份。

新增三个纯 CLR 原语：精确盒类型检测、精确拆箱、i64 wrapping add。
旧转换型 Unbox 与 checked Add 不改。Python 快慢路选择与溢出恢复属于 MIR；
codegen 只机械发 `isinst`、`unbox.any`、`add`，无新逐轮 C# ABI。
RHS 自身的属性读取或动态加法不在本切消除范围，不能声称整循环没有动态调用。

## 数据流与替代设计

按 ADR-0002，首切在现有可变局部 CFG 上建立有限前向 worklist：
入口未知、可达前驱交集、赋值 kill、精确类型测试真边 gen，并转移已证明的局部拷贝。
谓词或被测局部改写使对应关系失效；不对可重读 global / cell 推导事实。
MIR validator 拒绝没有精确事实的拆箱，避免错误 Pass 产生 CLR 类型异常。

本切不引入完整 SSA、phi 消解、全程序特化或任意逃逸分析。
只读 SSA 视图在复杂合流与后续优化上的收益仍需独立评估；有限分析不是全部 M3.9 验收。
保留旧 holder 实现供等语义对照，而不是恢复旧数据类静态路径的错误 eq 行为。

## 验收与决策门槛

必须覆盖双向溢出 / BigInteger 回落、bool / float、`__radd__` / `__iadd__`、
失败不提交状态、getter 次数、初值与返回盒身份，以及守卫后改写 / 合流绕过的结构负例。
CIL 的无 holder 表达只是结构证据；实际机器码体积、分配、冷 / 热耗时、
快路与动态回退样本共同决定是否默认启用。不得以更少 CIL call 单独宣称加速。
无可靠净收益则保持实验关闭，继续定位而不把明显慢实现直接列为可接受结论。

本实验可能增加 CFG 与机器码体积；收益假设是去除每调用 holder 分配、
改善局部状态的寄存器分配和 Tier0 成本。最终实测、默认状态与完整门禁结果待补。

## 首轮实验结果与下一步

第一版正确性结构 / 差分通过，但尚不具备默认启用的性能证据。
同运行时两轮交错配对测量中，禁 tier 的 bool 回退分别慢 33.1% / 16.0%；
其它短负载有明显进程间与轮次波动，不能挑最好一次宣称稳态提升。
同一分配诊断五次调用从 360 B 降至 160 B，净减 40 B / 调用，证实去除了 holder；
这也修正了先前仅凭字段布局估计 holder 48 B 的假设，不能把未测估算写成结果。

实际 `accumulate` FullOpts 机器码由 690 B 增至 1488 B、栈帧 72 B 增至 152 B。
原因线索是直接槽慢路复用了 `Rvalue::DynBinary`，后端选择的 `PyPic.Binary` 激进内联
再次展开多类型快路；旧 holder 内部却直接调用通用 `PyOps.Binary`。
第一版因此不是仅改变 holder 布局的隔离实验：必须同时记录这项调用选择差异。
原始分布、全部语义检查与汇编见
[`direct-first/README.md`](../../tests/perf/results/m3_9/direct-first/README.md)。

下一有界实验仅将这处已经失配的慢路显式选为既有 `RuntimeFn::DynBinary`，
调用与旧 holder 相同的 `PyOps.Binary`，避免在同一循环重复嵌入通用 PIC 快路。
普通动态算术的 PIC 不变，不新增 C# 逐轮接口。
该既有但未使用的 RuntimeFn 首参为 CLR int，须补 MIR 常量操作码验证及后端签名转换，
不能将 i64 压栈直接调用 int 签名。修改后重新跑同一正确性 / ABI / 配对测量；
目前仍是实验，不因节省对象就忽略吞吐退化。

## 冷路与状态压缩实验

第二版证实隔离冷路有效：同负载 FullOpts 从首版 1488 B 缩至 868 B，栈从 152 B
缩至 56 B（holder 基线为 690 B / 72 B），没有再展开整片 PIC 多类型分支。
但禁 tier 整数快路两组仍慢 14.7% / 34.1%，iadd 回退慢 27.8% / 10.2%；
不能只依据代码体积和分配改善默认启用。原始证据保留于
[`direct-cold/README.md`](../../tests/perf/results/m3_9/direct-cold/README.md)。

当前第三版实验把上述初版独立 dirty 标志压缩为旧 holder 已使用的盒缓存状态：
成功整数快加后原对象槽写 CLR null；仅 `is_integer && cached_box == CLR null`
才物化旧整数。非整数的真实 CLR null 不当作 dirty，Python None 是独立对象。
引用比较使用 MIR 的原生 Eq / CIL ceq，不调用 Python `__eq__`；
新增回归锁定 None 零轮、用户相等协议不得执行及原共享盒身份。
仅移除一个跨循环存活状态，不扩候选、不新增 runtime ABI，性能尚待配对验证。

## 第三版结果与默认决策

状态压缩未带来预期机器码收缩：`accumulate` FullOpts 868→865 B，
`field_reads` 2392→2398 B，栈空间未变。相同诊断分配仍净减 40 B / 调用。
为区分短样本中的 tier 晋级波动，另用独立 compiled 方法 harness：
20×200,000 轮额外预热，7×2,000,000 轮计时，三变体各三进程轮转，
计时期间不读分配、不采反汇编。默认 tier 的字段循环比 holder 快 6.5%，
禁 tier 仍慢 11.1%；纯 range 两轮禁 tier 慢 44.8% / 63.3%，没有证明可限定开启的收益形状。
这组充分预热结果单独列出，不混入原来三轮短预热的表。
完整证据见 [`direct-null/README.md`](../../tests/perf/results/m3_9/direct-null/README.md)。

决定不把整个默认路径换成直接局部方案。保留原正确 holder，提供显式编译会话选项
`--experimental-direct-accumulator`，让后续研究能复现直接方案而不影响默认用户程序。
MIR 共用严格候选，仅选择不同状态展开；默认与实验模式都需真实 Python 差分和结构验收。
不以环境变量、库名或基准函数名隐式切模式，不恢复更快但语义错误的旧数据类表示。

失败实验没有证明 JIT 方向无价值：它证明“少对象 / 更直白 CIL”不自动意味着更快，
需要让 JIT 同时获得更好的寄存器分配、冷路径隔离与调用边界。
保留精确类型事实分析、受验证原语及完整证据，下一竖切优先新鲜临时 tuple 标量替换；
每轮行号更新与索引装箱已是实际机器码中可见的后续研究点，尚未实现或宣称提速。
