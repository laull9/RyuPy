# ADR-0025：项目驱动Unicode基础内建

状态：已接受（直接调用）。

## 背景

固定wcwidth项目首阻断是ord。已有字符串存储使用.NET UTF-16，但Python按码点计数；
直接取首char会把补充平面字符拆错，Rune/ConvertFromUtf32则拒绝Python允许的孤立代理项。

## 决定

通过既有动态内建分派接入ord/chr，不引入额外后端ABI。ord检查一个UTF-16单元或合法代理对，
同时支持单字节bytes/bytearray；chr范围检查后BMP直接构造char字符串，补充平面使用合法代理对。
chr接受整数/bool与一次__index__，结果必须整数；先检查C int溢出，再检查Unicode范围。

一等内建函数值尚无统一运行时表示，ord/chr作为值显式E0305，不沿用旧通用内建值回落None的问题。
该缺口与map一起作为下一项目驱动任务。Unicode错误路径不透传CLR异常。

## 后果

ord成功路径无需枚举全串或额外容器；这是设计性质而非测得速度提升。chr分配结果字符串。
沿用当前UTF-16表示，完整字符串内部表示差异不在本切重写。按既有范围未新增warnings设施。
wcwidth首阻断实际前移至map，但仍有装饰器和系统API依赖，固定项目分子仍为0。

### 已知字符串表示限制（待修，不作为已接受性能偏差）

两个独立代理码点拼接为相邻高/低代理项后，当前UTF-16字符串无法保留来源区别，
`ord(chr(0xD800) + chr(0xDC00))`会返回65536，而CPython应TypeError。普通补充平面字符
与单独代理项已支持，不宣称所有代理串兼容。D009及独立pending记录该表示缺口，后续统一处理
字符串码点表示；本切不为此宽改所有字符串操作，亦无性能证据据此接受永久偏差。
