# ADR-0181：以随包 CPython provider 为兼容主线

- 状态：已接受目标与架构方向；实现待启动
- 日期：2026-11-13
- 决策来源：用户要求本轮只规划、整理文档，暂停开发
- 更新：ADR-0172 的实施顺序、ADR-0009 的近期目标与 M3.8 后排策略；既有语义、回归和历史验收保留

## 背景

逐模块 C# 标准库重写和逐库 C ABI 绑定已经积累真实成果，也持续产生独立的参数、
异常、对象、资源和分发适配。继续沿这条路径扩大生态，维护成本会随 API 数量增长。
现有 `tests/aot/stdlib_service/app.py` 已将 HTTP、编码解压、包资源和 SQLite 串成
一个应用，适合直接检验 provider 切换后的行为与真实搬迁。

## 决定

1. 近期主线改为**可随包分发的 libpython 宿主与通用对象桥**。CPython 自己加载
   标准库与扩展，RyuPy 编译的应用通过统一对象协议调用；新增兼容能力优先复用该路径。
2. 首先交付 standalone 目录包：原生入口、托管运行时所需产物、固定 CPython、标准库、
   扩展及非系统原生依赖和许可证一起发布。目标环境无需预装 Python、.NET 或 SDK。
3. 应用入口继续编译为 CIL / NativeAOT；CPython provider 模块可以由嵌入解释器执行。
   所有执行域在构建计划与报告中列明，整个应用交给解释器执行另列运行模式与指标。
4. CPython provider 是后续兼容配置的主路径；纯 RyuPy 配置保留为显式的轻量交付与性能路径。
   先显式试点，通过宿主、联合应用、NumPy 三道门后再切换默认兼容配置。当前 CLI 行为保持原样。
5. 保留 MIR / typed CIL、守卫特化、逃逸与装箱消除等能力。先测跨桥成本，随后按实测热点
   引入 C# 原生替换；替换仍须满足同一对象、异常和副作用合同。
6. 停止把新增标准库逐 API 重写、C ABI 签名扩张、历史 16/20 原生比例当作宿主的前置。
   既有 C ABI 用于显式外部库，保留维护；原生标准库实现保留回归与对照。

## 取舍

选择单进程嵌入 CPython，而非 Python 子进程 RPC：对象身份、可变别名、回调、扩展持有
和 buffer 能在同一进程设计统一合同。代价是承担 GIL、双堆生命周期和原生崩溃风险，
宿主因此面向受信任应用，安全隔离应放在进程或操作系统边界。

选择独立 C# CPython 互操作组件和最小 C shim。shim 封装版本相关初始化结构、宏以及
Python callable 代理；标准库和第三方包不在 shim 内逐个重写。互操作采用静态声明与
NativeAOT 可保留的回调入口，避免依赖运行时 IL 生成。

首轮锁定现有语言基线 CPython 3.12.13、常规 GIL 构建和单主解释器。构建产地与发行制品
须冻结来源、补丁版本、构建选项、ABI、架构和许可证；扩展锁定匹配 wheel 或可重建源码。
后续 Python 升级按独立兼容矩阵推进。第一轮只选 NumPy；pandas 在基础桥验证后追加。

长期目标是**对标 Nuitka 的 AOT 打包体验与兼容性，并以可测量的编译优化改善性能**。
AOT 明确指 RyuPy 编译部分和入口的提前编译，解释器执行的依赖保留执行域标签。
先完成目录包及三平台交付，再推进 onefile、增量构建和热点优化。

## 后果与验收

- 新主线分为 CP1 宿主与对象桥、CP2 同一联合应用搬迁、CP3 NumPy 扩展、CP4 分发和覆盖、CP5 性能。
- 产品兼容率、纯 RyuPy 原生执行率、JIT / NativeAOT、平台搬迁分别记录。保留固定 20 项原始入口与版本。
- 跨堆循环、异常往返、回调重入和关闭顺序属于首轮合同，不能通过复制对象或提前销毁绕过。
- 本 ADR 与配套文档属于规划交付；上述 CP 里程碑全部待实施。
