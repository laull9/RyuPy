# M2.2 异常体系与结构化清理

## 做了什么

把 `try` / `except` / `else` / `finally` 从 HIR 一路打通到 CIL 异常表，异常对象带上
`__cause__` / `__context__` / `args`，未捕获时按 CPython 的格式打印 traceback 并退出 1。

## 关键决策

1. **`except` 直接映射成 CIL 的类型化 catch。** 前提是 CLR 继承树与 Python 继承树同构：
   `PyZeroDivisionError : PyArithmeticError : PyException`。这样 `except ArithmeticError`
   能抓到 `ZeroDivisionError`，不需要在运行时手写类型匹配。代价是新增异常类型时必须
   同时改三个地方（运行时类、`PyExceptionTypes` 表、`EXCEPTION_TYPE_NAMES`）。
2. **`finally` 不用 CIL 的 finally。** CIL 的 finally 处理器不能 `leave` 离开、也无法抑制
   正在传播的异常，而 Python 的 `finally` 既要能 `return`（甚至覆盖返回值），也要能吞异常。
   改成「catch-all 异常通道 + 状态码 + 分派块」后，五种离开方式（正常 / return / break /
   continue / 异常）走同一套状态机，语义与 CPython 一致。
3. **受保护区间用「块下标区间」表示。** 构建器保证区域内的块连续分配，codegen 因此可以把
   块区间换算成指令区间，直接填异常表。窗口之外的块（handler、finally 体、after）必须在
   窗口关闭之后再分配——这条约束写在 `build_try.rs` 的每个分配点旁边。

## 踩到的坑

- **异常表顺序**。CLR 按顺序匹配，且要求内层子句排在外层之前。按 try 起点升序排序时，
  嵌套 try 一律 `InvalidProgramException`，而且没有任何提示。最后用「try 结束位置升序」
  作排序键，同一 try 的多个 catch 再按起点降序，才同时满足嵌套与源码顺序。
- **两条 catch 记录共用同一段 handler 指令**会被 CLR 当成重复子句。所以每个类型配一个
  独立的两指令入口（`stloc` + `leave`），也顺便让 handler 长度可以静态给出。
- **`leave` 的目标待定**。`finally` 入口块必须在窗口关闭后才分配，构建期还不知道地址；
  用「待回填块列表」先记下来。注意这类块此刻还没有终结符，如果不立刻换一个新块继续构建，
  后面的语句会被错误地接到它后面——`break` 之后的语句「多执行一次」就是这么来的。
- **`WithCause` 不能按类型名重建对象**。基类方法里 `new PyBaseException(...)` 会让
  `except RuntimeError` 永远抓不到，而 traceback 看起来完全正常。改用 `MemberwiseClone`。
- **隐式 `return None` 也要写返回槽位**。动态函数返回 `object`，尾块 `ret` 之前没有值
  会生成非法 IL。

## 还没做

- 索引 / 键 / 名称错误的统一映射（要等 M2.3 的容器）。
- 用户自定义异常类（M2.6）。
- 完整 frame 对象、`__traceback__` 的可访问表示与 `sys._getframe`：暂缓。
