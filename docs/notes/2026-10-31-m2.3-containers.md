# M2.3 容器与可变别名

> 日期：2026-10-31 ｜ 状态：已完成（4 个 e2e 用例转正，`make check` 全绿）
>
> 本文记录 list / tuple / dict / set / bytes 落地时的关键决策，以及过程中挖出的三个语义 bug。

## 1. 目标与范围

M2.3 要让「容器」从「编译期拒绝」变成「运行时正确」。范围严格限定四件事：

1. **构造与访问**：list / tuple / dict / set / frozenset / bytes / bytearray 的字面量、下标、切片；
2. **可变别名**：容器赋值只复制引用，两个变量必须看到同一份数据；
3. **相等与哈希**：`True == 1 == 1.0`、字典保持插入顺序、不可哈希对象显式报错；
4. **迭代协议**：与 M2.4 的 `for` 对接，并能在「迭代期间修改」时按 Python 规则失败。

推导式、生成器、`str` 的完整方法表不在此列——前者是 M3.1，后者是 M2.4。

## 2. 类型层的决策：容器一律降级为 `Dynamic`

最容易纠结的一点是「要不要为 `list[int]` 做静态特化」。结论是**不做**，理由是边际收益不匹配：

- Python 的 list 本来就可容纳任意对象，`list[int]` 只在少数热点里成立；
- 一旦引入参数化容器类型，下标、切片、`append` 的类型推导要同时覆盖协变与泛型一致性，成本远超收益；
- 真正需要性能的地方在 M2.5 之后可以用 shape / 类型反馈做，而不是在类型系统里堆复杂度。

因此 `Ty` 对容器表达式、`Subscript`、`Slice`、`ForEach` 的目标变量统一走 `soft_demote`：不是「报错」，而是把整条表达式连同上下文降级为 `Dynamic`，交给 `PyOps` 处理。MIR 侧新增一组运行时调用：

| MIR | 作用 |
| --- | --- |
| `MakeList` / `MakeTuple` / `MakeSet` / `MakeDict` / `MakeBytes` / `MakeSlice` | 构造；除 slice / bytes / dict 用普通 `Call` 外，其余用 `CallWithArgs`（见下） |
| `GetItem` / `SetItem` / `DelItem` | 统一的下标协议，负索引与越界在运行时处理 |
| `Len` / `Contains` / `IsSame` / `ReprValue` | 长度、成员、`is`、repr |
| `UnpackCheck` | 星号解包的长度校验（≥ 非星号目标个数） |
| `IterStart` / `IterNextOk` / `IterValue` | 迭代协议的三段式：**能否继续**与**取值**分开，才能在循环条件处干净地分支 |

### 2.1 可变参数怎么过 CIL：`CallWithArgs`

`MakeList` 这类调用的参数个数编译期已知，但 CIL 的 `newarr` + `stelem` 序列在栈化器里要精确保持「数组引用在栈底、下标、值」的顺序。做法是新增 `Rvalue::CallWithArgs { callee, prefix, args }`：先把 `prefix`（如 `len` 的名字）压栈，再建定长 `object[]`，逐个 `dup → 下标 → 元素 → stelem`，最后 `call`。

`lower_object_array` 里最容易写错的是**忘记 `Duplicate`**：`stelem` 会吃掉数组引用与两个操作数，少一次 `dup` 第二个元素就无处安放。这个 bug 表现为「只有最后一个元素进到了数组里」，排查成本不低。

## 3. 三个语义 bug（都不是编译错误，是静默错值）

这一轮的收获几乎全在这儿。它们的共同点是：**程序照常跑、照常输出，只是答案不对**。

### 3.1 int / float 相等丢失精度

`PyHash.NumericEqual` 最初对混合类型的处理是把两边都转成 `double` 再比：

```csharp
double da = PyOps.ToDouble(a);
double db = PyOps.ToDouble(b);
return da == db;   // ← 错
```

于是 `9007199254740993 == 9007199254740992.0` 得到 `True`，而 CPython 是 `False`——前者超出 `double` 的 53 位尾数，转过去就变成了后者。修法是混合情形一律走 `PyInt.CompareWithDouble`（用 `BigInteger` 对 `double` 精确比较），只有真正两边都是 `double` 时才用 `==`。

> 教训：**任何「先统一成 double 再比较」的写法都值得怀疑**。float 与 int 的交界处默认就有精度陷阱，宁可多一层 `CompareWithDouble` 调用。

### 3.2 `nan == nan`

`PyHash.Equal` 开头有一句看似无害的快判：

```csharp
if (ReferenceEquals(a, b)) return true;
```

它对绝大多数类型成立，唯独 NaN 不成立——`nan = float("nan"); nan == nan` 在 Python 里是 `False`，即便两侧是同一个对象。这条 bug 藏得很深：容器相关的 e2e 用例长期把 `float` 当普通数值用，直到把显式 `nan` 比较写进单元测试才暴露出来。修法是把 NaN 判断排到身份判断**之前**。

### 3.3 `print` 边求值边输出

原来的 `print` 降级是「算一个写一个」：

```text
for arg in args: Write(eval(arg))
```

这与 Python 的调用语义相悖：CPython 先求值**全部**实参，再进入函数。差异在两个地方可见——

- `print(x, x.pop())` 打印的是 `pop` 之前的内容；
- 实参里有嵌套 `print` 时，输出顺序会交错。

改为先生成全部实参的 MIR 临时量，再按序输出。这同时让快照里的语句顺序变「合理」了：`BitOr` / `Add` 这些计算全部排在写之前。

> 教训：**把「顺手写求值」下沉到代码生成层最危险**。求值顺序属于语言语义，不是实现细节；一旦在 MIR 里定死，后面所有 Pass 都会把它当成真实语义来优化。

## 4. 相等性与哈希的分工

`==` 与「字典键匹配」在 CPython 里不是同一个函数：前者走 `PyObject_RichCompare`，后者走带指针快判的 `PyObject_RichCompareBool`。这个区别直接决定了能不能把 `nan` 用作键——

| 情形 | CPython | 本实现 |
| --- | --- | --- |
| `nan == nan` | `False` | `PyHash.Equal` 中 NaN 判断优先于身份判断 |
| `d = {}; d[nan] = 1; d[nan]` | `1` | `PyKeyComparer.Equals` 加 `ReferenceEquals` 快判 |

因此 `PyHash.Equal` **不含**身份兜底，而 `PyKeyComparer` **含有**，两者不能合并到一个函数里。文件头部的注释专门写了这一点，避免以后被「顺手统一」。

`set` / `frozenset` 的 `|` `&` `^` `-` 同样值得注意：它们与整数的位运算共用语法，但语义不同。`PyOps.Binary` 里先尝试集合语义（`SetUnion` 等），不命中再回退到整数要求的 `RequireInts`，这样 `{1} | {2}` 与 `1 | 2` 都正确。
