# 2026-10-31 M2.0 实现总结：项目基线、用例框架与动态值 ABI

- 日期：2026-10-31
- 关联里程碑 / ADR：[M2.0 项目基线与测试入口](../../TODO.md)、[ADR-0010](../adr/0010-dynamic-value-representation.md)（取代 ADR-0003）

## 做了什么

### 1. 用例框架从「单文件 + stdout」扩到「目录用例 + 错误路径」

Phase 1 的 e2e 只能表达一种用例：单文件、无参数、期望成功、比较 stdout。Phase 2 要覆盖多文件
入口、命令行参数、环境变量、标准输入，以及**错误路径**（退出码 / 异常类型 / 消息 / 异常链），
于是把发现、解析、匹配、记录拆进 `ryupy-e2e` 库，测试与项目 runner 共用：

- `tests/cases/**/case.txt`：行式 `key = value` 清单，声明 `entry` / `args` / `env` / `stdin` /
  `cwd` / `expect_exit` / `expect_exception` / `expect_cause` / `expect_stdout` / `pending`；
- 同目录其它 `.py` 是辅助文件，不会被当成独立用例——多文件 fixture 与入口的界限由清单决定，
  不靠目录名约定；
- 错误路径只比较最后一行异常与 cause 行，traceback 栈帧属框架差异，不参与比较；
- 清单先用 CPython 校验：声明的退出码 / 异常与解释器实际行为不符时，两边都直接失败，
  避免「清单写错但测试通过」；
- 结果写 `target/e2e/results.jsonl`，状态分 `passed` / `failed` / `pending` / `unexpected-pass`，
  pending 不计入通过，跑通时打印 `[可转正]`。

`make cases-selftest`（`E2E_PYTHON_ONLY=1`）只跑 CPython 侧，用来证明框架本身把参数、环境、
stdin 与多文件入口真的传给了子进程——两个 `harness` 用例因此在 RyuPy 支持 `sys` 之前就有价值。

### 2. 冻结 20 个项目并记录 CPython 基线

`tests/projects/manifest.tsv` 固定 20 个纯 Python 项目（6 类用途），`fetch_projects.py` 从 PyPI
拉 sdist 并用 `lock.tsv` 锁定 URL 与 sha256，`run_projects_baseline.py` 用固定 CPython 3.12.13
记录每个项目入口样例的 stdout / 退出码 / stderr 末行。

`ryupy-e2e --bin projects` 编译并运行同一入口，对照基线，输出 JSONL 与
`native / unsupported / failed / not-evaluated` 分类。当前 0/20 native，全部阻塞在
「不支持普通 import」（M2.7）——这正是 M2.0 想要的失败账本。

### 3. 动态值 ABI 定稿（ADR-0010）

写了布局基准（2000 万次迭代，.NET 10 Release）：

| 场景 | object 装箱 | 24B struct |
| --- | --- | --- |
| 算术累加 | 41 ms | 4 ms |
| 容器读写 | 101 ms | 9 ms |

结论：M2.1 起 `MirType::Dynamic` 用 `System.Object`。理由写在 ADR 里，核心是「对象模型本来就
是引用」+「热点数值路径由静态特化承担」。运行时新增 `PyOps`（操作码分派的统一运算 ABI）、
`PyInt`（long→BigInteger 升级）、`PyRepr` / `PyNone`、`PyBaseException` 家族与 `PyCast`
（拆箱），42 项 xUnit 锁定算术、精确比较、NaN、真值与错误消息。

## 踩到的坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `manifest.tsv` 第一行被当成数据行 | 文件带 UTF-8 BOM，`startswith("#")` 失效 | 去掉 BOM；解析器统一 `utf-8-sig` / `trim_start_matches('\u{feff}')` |
| 20 个项目基线全部 `ModuleNotFoundError` | sdist 解开后多一层 `<name>-<version>/`，部分还是 `src/` 布局 | `package_root()` 逐层下探，`src/` 存在时再进一层 |
| 入口样例导入到自己 | 样例文件与包同名（`six.py`），脚本目录先于 PYTHONPATH | 入口统一命名 `<id>_sample.py`，并在文档里写明原因 |
| 沙箱里 `shutil.rmtree` 报 `EISDIR` | 递归删除被拦截 | 抓取脚本改为幂等解包：已存在就复用，不删目录 |
| 结果文件总是空的 | libtest-mimic 多线程跑用例，`thread_local` 收集不到 | 换成 `Mutex<Vec<_>>` |
| `Normalize` 永远返回 BigInteger | C# 三元表达式 `? (long)v : v` 被统一成 BigInteger（long 可隐式转换） | 改写成 if/else，并把这个坑写进注释与测试 |

## 学到的概念

- **测试清单本身也要有「答案」**：错误用例的期望由 CPython 先行验证，清单写错必须让两边同时
  失败，否则会长期存在「假通过」。
- **pending 的两种错法**：真没实现（应当 pending）与已经能跑（应当转正）。后者需要显式提示，
  否则 pending 会变成永久墓碑。
- **装箱 ABI 的取舍不是「快慢」而是「表示统一」**：容器、实例、异常、模块全局都是引用槽位，
  值类型表示进入这些槽位仍要装箱；省下的是纯算术循环里的分配。

## 还没想明白的

- 动态函数的「静态特化 + 通用回退」双版本要不要真的编译两遍？当前计划是按调用点的一致性
  逐函数降级（静态 → 动态），代价是同一个函数在所有调用点都走动态路径。等项目数据再定。
- `PyOps.Binary` 每次多一次 `switch`。装箱成本已经占大头，暂不为分派做专门优化。
- 项目 runner 现在只跑入口样例，上游测试范围还是文字描述。Phase 3 要把「指定范围通过」变成
  可执行的上游测试子集。
