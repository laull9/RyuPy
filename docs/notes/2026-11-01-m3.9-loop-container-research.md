## 1. 已知迭代融合：新鲜小 tuple 的 for

真实输入：`for value in (a,b,c): total += value`。
真实 MIR：入口 MakeTuple([_0,_1,_2]) → IterStart；条件块 IterNextOk；
循环体 IterValue → 动态 +=。当前 TupleScalar 因 IterStart 是非白名单使用而保留对象。
接点：build_loops.rs::build_for_each；PyIter.Create(PyTuple) 与 PyIter.MoveNext/Current。

最窄候选：≤8 项新鲜 tuple，只有唯一 IterStart 消费；iterator 只有固定自然循环的
IterNextOk/IterValue 使用，禁止任何 alias/return/传调用/identity/帧保存。
可在 MIR 保存构造点元素快照，以私有 i64 index 和有限选择块替换 iterator 状态；
保原循环体和 break/continue/else 边，不复制用户循环体，不做 whole SSA。
目标是消除 object[]、PyTuple 与 PyIter 分配，以及每轮迭代协议分派。
不新增 C# 解释器或逐轮桥接 helper；收益与代码尺寸需 JIT 验证。

必须阻断：已有变量 tuple/自定义 __iter__/暴露的 iterator、EH/yield、循环状态被观察。
元素求值一次且在首次迭代前；元素对象身份保留；用户体 += 可能回调/抛错，不得提前求和。
空 tuple 不写循环变量；break 不运行 else，continue 正确推进；重绑定 a/b 不影响已冻结元素。
正反测试：有副作用 RHS、空迭代、break/continue/else、元素回调修改原变量、返回 iterator 逃逸。
收益入口：本 probe 的 tuple_iteration，分别空/3/8元素，按调用计 allocated bytes；
体只消费最后值与体带动态累加分开测，避免将累加器变化误归融合。

## 2. LICM：只上提无抛错的静态整数位运算

真实输入：带完整 int 标注的 invariant(n,a,b)，循环里 `total += (a ^ b) & 255`。
真实 MIR bb2 每轮 BitXor(_1,_2)→BitAnd(...,255)；_1/_2 参数在循环内无写；
range 已在入口冻结 stop，直接 i64 CFG，不需要再造 range 迭代器。

最窄候选：单入口自然循环、支配前置块；I64 BitAnd/BitOr/BitXor 以及 Bool 纯比较，
操作数为循环外唯一到达定义，目的临时不在循环首轮定义前读取。
有限 fixed-point 收集依赖于已知 invariant 的纯节点，移动到前置块；保持 Line/trace标记。
不做全程序 SSA；不从 Python 注解推断动态用户对象纯性。

明确禁止：checked Add/Sub/Mul、除法/移位、Unbox/PyCast、Box（身份）、
GetAttr/GetItem/Len（回调或可变容器）、所有 runtime calls、EH/yield。
即使 x*x 看似不变，零迭代不应新抛 OverflowError；非空时错误发生行/顺序也不能前移。
普通属性能运行 descriptor，list 的 len 可变，不能借 LICM 缓存。

收益入口：上述 invariant，空/大循环与参数重写负例；查 Tier1 nativecode 中两条位指令位置。
.NET JIT 很可能已自行上提此类纯 CIL，因此这是低风险但可能零收益的候选：
必须先看默认 tier/禁tier汇编，若已消除每轮计算，保持当前实现即可，不以更短MIR宣称提速。

## 3. 容器特化：exact PyList + 已知 i64 下标走已有 long 重载

真实输入：list_index(n,values)，循环里 `total += values[0]`。
真实 MIR bb2：Box<I64>(0)→RuntimeFn::GetItem(_1,boxedIndex)→NumericAccumulatorAdd。
运行时 PyIndexing.GetItem 先分派对象；sealed PyList.GetItem(object) 再分派 key，
最终转到现有 `PyList.GetItem(long)`，由 Normalize 保负数与越界 Python IndexError。
PyList.Items 是 List<object?>；不应直接读 CLR List.get_Item 绕过 Normalize。

可行窄候选：MIR 对冻结的 receiver 作 CLR exact PyList 守卫，已知原生 i64 索引走
现有实例 GetItem(long)；其它对象/索引保 RuntimeFn::GetItem。这不需要新 C# helper，
但需要显式 MIR/native-call签名与机械 codegen引用、守卫验证，不可让codegen猜Python类型。
类型 guard 若上提到入口必须证明 receiver local 循环不重绑定；否则在原读取点守卫。
sealed PyList 没有用户子类 override，不能泛化到任意 list-like 或用户 __getitem__。

不得缓存 length、Items[index] 值或用户可变数组指针：循环体 __radd__ 可能修改同一list，
下一次读取必须见到变更。负数规范化/边界检查必须每次做，不能按初始len预证明。
参数不是list时原 __getitem__ 回调次数与抛错行不变；n=0不应新抛索引异常。
索引仍为动态对象/__index__时保原路径，不把bool/BigInteger隐式截断为i64。

收益入口：probe list_index 加普通list/tuple/用户对象与回调修改list三组，
固定0索引装箱已有字面量池，预期节省主要是对象/key分派，不应声称每轮少一次真实装箱分配。
检测 Tier1 是否已内联 GetItem(object) 并去掉类型检查；若现JIT已做到则拒绝增加MIR复杂度。
