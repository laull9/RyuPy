# M3.10 NumericList受控背板pilot：runtime契约与审计

状态：runtime焦点验收已过，编译器整合/完整门禁待验；不等于通用Dynamic union ABI。仅编译器证明fresh唯一sink
的构造路径使用PyNumericListOps.Create/AppendF64；普通list构造仍是object槽。

## 布局和身份

首轮单object背板在三臂测量中严重回退，唯一根因修正改为typed _items与_numeric两个引用字段，
普通包装对象因此多8B；普通热路直接访问List<object?>，数值模式仅_numeric有效。数值槽为独立object引用+long bits的16B顺序布局，引用不与数值重叠。
Fresh F64槽用内部哨兵，首次GetItem物化并回写同一槽的盒；后续相同槽返回同一引用。
已存在boxed double通过普通Append进入时保原引用+原bits，重复append(x)不生成不同盒。
-0与NaN按原位模式保存，不做值规范化。default槽无效，不能当None或0；误读为PyRuntimeError。

Items不是并行缓存：完整构造object后备列表成功后才发布_items、清空_numeric并永久退出数值模式。
数值背板不再可达。后续调用AppendF64也只普通装箱追加，不重新启用数值模式，避免已交给
旧调用者的可变Items引用与新背板分裂。普通Append异构对象触发退化，double保原盒留数值模式；
其余通用写入保守走Items退化。没有改变Python可见list类型或可变别名语义。

## 全部公开路径审计

| 路径 | 处理 |
|---|---|
| Count/Truthy/Normalize | 只读背板计数，不物化；Normalize不再经Items |
| GetItem(long) | 单槽物化缓存，不退化其它槽 |
| SetItem/DelItem/Insert/Pop/Clear/Reverse/Sort等 | 现有Items入口先完整退化，再执行原逻辑 |
| Copy/GetSlice/repeat/concat/ToSequence | 读原列表Items后复制原引用，保重复引用和NaN身份 |
| PyHash.SequenceEqual、repr、公开容器操作 | 原有Items入口完整退化，不私自复制fresh槽 |
| PyIter | 创建保原list；Current在暴露第一个元素前读Items并完整退化，保持后续实时append可见 |
| 返回Items给外部C#调用者 | 永久同一object列表，之后所有读写都以该列表为准 |

不存在返回内部List<Slot>或修改其内容的Python入口。数值slot/list辅助成员均内部使用。
测试反射只检查背板/非法default状态，不进入生产AOT路径。

## 精确guard ABI

Create()->object；AppendF64(object,double)->object（PyNone.Instance）；
PeekList(object,object)->object?（失败CLR null）；CanReadF64(object,object)->bool；
ReadF64(object,object)->double。

Peek/Can仅接受sealed PyList、actual boxed long及范围内下标，不调用__index__/__getitem__、
不读取Items、不物化、不分配；支持负下标，long.MinValue预检不会溢出。
Peek只从普通object背板读子PyList；Can/Read在对象背板仅接受actual double，也能读数值槽。
Read防误用仍抛PyTypeError/PyIndexError，不泄漏CLR越界/强转异常。
编译器不得在guard与Read之间插入用户回调或可能改写列表的操作；并发无GIL模型不在该pilot。

## 性能风险（必须量化）

普通对象槽保持8B，PyList包装对象两引用（比原普通对象多8B），Count/GetItem/Append新增null模式分支，
绝不宣称普通路径零成本。需要普通Count/GetItem/append与数值构造/纯读/退化的配对测量。
数值背板16B槽减少fresh double盒，但混合引用/低复用/很快Items退化可能增加峰值内存与复制。
当前8项专测已覆盖缓存身份、已有盒/NaN、切片/重复/迭代、永久退化、纯guard与错误、
非法default槽、普通背板和重复guard/read零分配；与6项PyHash测试合计14/14通过。
生产默认启用仍须编译器证明与后续完整门禁，不将runtime通过当成完整优化通过。

## 焦点测试揭示并修复的既有序列身份缺口

首轮6/7，数值copy的同槽盒引用检查已通过，但PyHash.SequenceEqual对共享NaN仍返回False。
原因是旧容器元素直接调用Equal，而直接NaN相等有意在引用检查前返回False。固定CPython
3.12.13中直接n==n为False，但[n]==[n]与(n,)==(n,)为True。
按授权仅把SequenceEqual改为左右元素各读取一次、引用相同则接受，否则Equal；未更改直接
NaN规则。新增普通object list/tuple的共享与不同NaN用例，原NumericList身份断言不删。
首失败日志/tmp/ryupy-m3_10-numeric-list-focused.log与修复后focused2.log均保留。
随后按授权对list.index/contains作同一必要修复：取元素一次，引用相同则命中，否则Equal；
补普通/numeric同盒NaN和不同盒用例，focused3合计14/14通过。dict值相等的同类旧缺口
仅登记待修，未在此pilot扩展。

## 守卫失败后的通用索引路径

集成差分暴露旧list仅接受bool/int/long而拒绝用户`__index__`。本次必要窄补仅list：
直接接受PyInt整数（含BigInteger），其它对象调用一次`__index__`并验证实际整数；超i64
报IndexError，协议返回bool沿现有明确NotImplementedError边界，不静默漏弃用警告。
回调结束后才Normalize，观察回调改变后的长度与背板，不缓存回调前槽或Count。
新增普通/numeric正负索引、非法返回、超范围及回调resize/退化后读写删除回归，
NumericList9项+PyHash6项合计15/15通过；日志
`/tmp/ryupy-m3_10-numeric-list-index-focused.log`。不扩tuple/bytes/slice协议。


## 首轮不利结果后的唯一修正

首轮禁tier matmul A/B调用体机器码完全相同（2879B），但B runtime普通读显著变慢；
C内层保留5个未内联探测/读取call（3059B）。这些是caller证据，不伪称已看到callee机器码。
源码另定位新ToIndex每个long都提前TypeName并走整数分类；恢复long/int/bool直接返回，
协议/BigInteger进NoInlining慢路，仅错误时求TypeName。不能把全部回退归因16B布局。

修正普通Items/Count/GetItem/Append直接typed背板，GetItem一次取Count并检查范围；
数值物化和错误路径冷分离，小型固定ABI与叶方法标记AggressiveInlining。该标记不是
保证JIT消除重复guard，更不是速度结果；必须用第二且最后预定矩阵验收，保留首轮负结果。
身份与先完整构造后永久发布契约不变，测试另验证两背板恰好一者有效。
