# 真实 list 派生：身份与存储分开

## 为什么先修基础协议

固定 docopt 原入口同时需要 list 和 dict 派生。先用精确 list 修空切片、负步删除、
extend 流式失败与永久耗尽，再引入独立布局，才能分清“旧协议缺陷”与“新载体接线漏项”。
支持 list 后不能把仍有 dict 阻断的项目记为通过。

## 一个可变对象，两个内部载体

新 PyListInstance 是公开对象，固定持有 PyList 存储。普通实例不增加字段，精确 PyList
保 sealed 和既有背板；代价是派生对象额外分配和存储间接访问。重初始化、+=、*= 必须
保 wrapper 身份与旧游标引用；copy、slice、+、* 只生成精确 list，不复制业务属性。

类发布仍沿隐藏类壳和公开槽分离：验证、分配、完成、装饰器都成功后才更新公开绑定。
根描述符需要绑定原 wrapper，并绕过派生的同名普通方法；不能把 list 根槽注入所有对象。

## 审查不只问“能否迭代”

独立反例发现四处遗漏：Unicode 排序把 UTF-16 当码点、dataclass 接受可变默认值、
foreign != 被当成 eq 取反、Iterator ABC 看不到继承根 iter。前三种“能运行但结果错”
特别容易被普通成功例掩盖。Unicode 在本切明确收窄支持域，其余三项保原源修复并逐字对照。
原 CP golden 不为实现方便改写，未支持合法域继续保留 pending。

## 测性能也要保失败

同一生成 CIL 和宿主测出精确 list 方法热路约两倍回退。新条件每次调用 PyType.Get 查询
canonical list，虽没有新增分配，仍付了字典查找成本。前置 PyType 类型短路可让普通
接收者不进入该查询，并保真实身份语义。最终量测见 ADR0104；共享机器时不能用聚合均值
遮盖慢例，也不能将不同构造实现的低分配说成 wrapper 免费。

## 留下的边界

用户核心 magic、回调排序、非 BMP 排序、宽或自定义 slice、copy/deepcopy 未在本切开放。
这些边界各自需要原生 CP 合同和成本审查，不按某个项目名称特判。完整行为与验收范围见
[ADR0104](../adr/0104-list-subclass-layout.md)。
