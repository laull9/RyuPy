# M3.10 动态值表示复评：对象、16B哨兵联合与24B显式标签

状态：架构/独立实验，不是生产ABI迁移授权。现有F64循环优化继续独立验收。
本记录不把数值子集实验当作完整Python性能，也不重用ADR0010的异平台旧时延作基准。

## 先纠正两个前提

ADR0003指出引用与数值字段不能重叠，这一CLR/GC约束仍成立。合法方案把object引用槽与
8字节数值bits分开；long/double只共享数值bits。16B用私有静态对象哨兵标类型，24B把
独立标签放在第三个对齐字。default(struct)必须表示Unbound，不可混同Python None。

ADR0010“容器/实例要求引用语义，所以struct进容器必装箱”不普遍成立：PyValue[]、
List<PyValue>、值类型字段能内联存储并让GC扫描独立引用字段。容器本身仍是引用对象。
真正约束是当前ABI和身份协议；其对象模型不是禁止typed容器的CLR硬限制。

ADR0010旧文字称数值is按值处理，也不能作为本轮放宽依据。当前PyOps.Is只对bool与
小整数特殊处理，其余先看实际引用；现有累加器/SSA物化保留初值盒和用户返回盒。
新表示必须保存这些已验收行为，而不是恢复旧过时论证。

## 当前落点

- codegen types.rs把MirType::Dynamic的局部、参数和字段都映射System.Object。
- PyCall/绑定器采用object参数、object[]位置/关键字/defaults/env，返回object。
- PyList.Items是List<object?>；PyDict索引Dictionary<object,int>，keys/values为object列表。
- PyInstance槽、generator frame与许多异常args、模块绑定/原生API都使用object引用。
- 当前选择性CIL路径已经可用多个未装箱局部+原盒/dirty标志，边界才物化。

因此“把一个struct加进runtime”不等于改好动态ABI。若全部返回又立刻转object，
收益会被边界分配/结构复制吃掉；如果把struct自身装箱成object，还会多一个结构盒。

## 三候选与不可省略的成本

| 候选 | 优点 | 风险/必须测量 |
|---|---|---|
| object + 选择性CIL局部 | 保持现有ABI/身份；局部可标量替换、无结构拷贝 | 每个有收益的区域需守卫/逃逸证明；未知容器读取仍是引用 |
| 16B sentinel-ref+bits | 比24B密；类型判别是私有对象引用比较；合法GC布局 | 数字也携带GC引用；数组写可能涉及写屏障；每次调用两字段搬运；类型哨兵加载不必然优于byte标签 |
| 24B tag+bits+ref | 标签直接；数值引用字段可置null；可保已有对象 | 槽位是object[]的3倍；调用可能隐式retbuf/栈复制，寄存器压力及GC数组扫描成本 |

JIT在内联时可能消去整个struct，也可能在有引用/分支时留栈；不能从C#大小直接推断
最终寄存器分配。`in`参数也不自动更快，地址暴露可能阻碍标量提升。必须同时看无内联
调用与内联循环，保存实际JIT反汇编，不用仅算术一个点选ABI。

## 身份是第一门槛

简单反例：fresh numeric x按值复制给y，两者以后分别lazy boxing会创建不同盒；
x is y或[x,x]的两次取值因此错误。即使24B有object字段，复制时尚为空也无法让之后
两个副本的物化互相可见。float NaN的容器身份快路使问题不只涉及显式is/id。

安全的局部协议：

1. FromExisting(object)保留已有对象引用（包括数字盒）；不因它能拆成long就丢原身份。
2. FreshNumeric只在证明身份未观察的区域使用；别名分叉/逃逸时统一物化并共享结果。
3. object边界保持原用户返回对象、异常args/defaults/闭包捕获等关系；失败不得提交新状态。
4. typed容器仅提供内部无观察读取不能自动使Python取值安全。重复槽、切片/重复列表等
   操作必须保共同来源，不能各槽独立懒装箱后冒充同一Python对象。

另一候选是把24B第三字打包为type+origin-id。新数值结果分配整数ID，复制保ID，is/id
与NaN容器快路识别同ID；这样未必每数字都要identity holder。但必须设计跨线程唯一性、
计数溢出、每结果ID生成的成本、object桥接关联以及整个runtime的身份快路迁移。
origin→box强表会永久保活历史数字；弱表需回收/清理，单靠弱缓存也不能保证所有object
快路都懂原身份。ID方案是待测设计，不是本原型已证明正确的全ABI替换。

## 独立原型与测量边界

scratch `/tmp/ryupy-union-prototype`，不引用/改写生产ABI。对称数值子集仅long/double/
bool/BigInteger，未知用户算术不是实现范围。这里不承诺这些类型的全部笛卡尔组合：
实际语义check锁定long+long溢出升级、bool+long和long+double；boxed BigInteger与float
混合在此Numeric.Add中使用Convert.ToDouble(object)，没有生产PyOps的显式转换/溢出协议，
所以该组合不在已验证正确范围。object步长预先装箱，避免把循环内常量盒
人为计入对照；选择性local是已知无溢出的下界，不冒充完整动态操作成本。

矩阵：整数/浮点累加；NoInlining按值调用和in调用；跨object接口往返；64槽数值容器
读改写；4096槽纯引用容器读写。后者检查union增加槽密度/复制开销，不只挑有利的数字。
每个结果检查；语义检查包含原盒别名、小整数/bool规范盒、None/Unbound、BigInteger升级、
混合数字、-0位模式，以及强制压缩GC后仅由struct数组引用的对象仍存活。
朴素fresh副本物化身份失败被作为预期反例输出，绝不把该模式声明为安全全Python表示。

在主线程独占窗口完成一次矩阵与既定反汇编采样，无工具失败/追加重测。原始数据与源码归档位置为
`tests/perf/results/m3_10/union-prototype/`。共享Linux x86_64/.NET10环境，默认/禁tier
各3新进程×7轮；布局用Unsafe.SizeOf，引用性用RuntimeHelpers，不用非托管布局猜测。

## 实际结果：有价值，但不是通用替换胜出

布局验证确为16/24B，两个struct均ContainsRefs=true；强制压缩GC保留数组中的引用。
原盒别名正确，小整数/bool规范盒、None/Unbound、溢出BigInteger及-0检查通过。
naiveImmediateAlias=False是刻意暴露的语义失败，不是Python兼容通过。

以下每行100万次操作，时延为各进程7轮中位数再取3进程中位数；分配是单轮总量。
内部初始化/最终返回盒的小固定开销计入，未从结果扣除。对象步长已预盒。

| 浮点累加 | 22.396 / 30.007 | 4.507 / 13.118 | 3.193 / 12.835 | 24000048 / 24 / 24 B |
| NoInline按值调用 | 18.274 / 10.314 | 8.455 / 3.249 | 32.797 / 11.529 | 24000024 / 48 / 48 B |
| NoInline in调用 | 同上object入口 | 12.341 / 3.352 | 15.616 / 5.047 | 同上 |
| 经object接口往返 | 18.274 / 10.314 | 20.369 / 21.656 | 21.991 / 23.869 | 24000024 / 48000048 / 48000048 B |

已知无溢出的选择性i64局部为默认0.456/禁tier0.360ms，单轮24B最终返回盒，明显优于
本泛型union整数循环。该下界不承担通用动态type/overflow协议，不能直接说同语义快数十倍。

最重要的正证据：typed数组可以避免每次新数字盒，两种tier的数值容器均显著改善，
直接反驳“进容器必装箱”。最重要的反证据：跨旧object ABI需要物化输入与结果盒，
本例分配翻倍且禁tier约慢一倍；24B纯引用容器放大空间和时间，NoInline按值调用也不胜。
不能只拿默认tier整数加速选全ABI，禁tier两个union整数实现反而比object慢。
浮点对照还包含操作分派差异：object走Numeric.Add/Convert.ToDouble，union exactfloat走
位转换与原生Add，不能把其时延倍数归因于16/24B布局单一变量。

这些是同一场景顺序、有限预热协议的共享执行器样本，默认tier含tier/PGO行为，
并非证明全部达到稳定最终JIT状态。禁tier24B引用数组进程中位数8.876/10.146/17.172ms
也有波动；全部进程原值已保留，没有筛选最快进程。不外推CPU/架构或全项目速度。

### JIT因果证据（禁tier FullOpts）

- Numeric.Call16的值参数在RDI/RSI、结果在RAX/RDX，没有结构返回缓冲；仍有40B栈区，
  不是完全无栈。函数机器码203B。
- Numeric.Call24从调用栈搬入24B参数，RDI为隐式返回缓冲；返回写引用调用
  CORINFO_HELP_CHECKED_ASSIGN_REF，再写bits/tag，栈区72B，代码256B。
  in24仍有返回缓冲/引用写帮助函数，只改善输入形态，不能声称所有拷贝消失。
- Work.Arithmetic16/24即使Add内联，循环中仍可见结构栈槽搬运/标签分支，栈区56/96B。
  这给“无分配却不一定快”提供具体解释；不是仅从C#的16/24尺寸猜测JIT行为。
- 精确汇编见jit-calls.txt和jit-arithmetic.txt；引用数组的写屏障/GC扫描代价未另做
  专用汇编归因，不能把表中差值全部归到单一屏障。GC压力/长寿命容器仍需下一轮专门测。

### 这次实验不证明的内容

没有测完整PyOps用户回调、真实Python调用绑定器、dict键哈希/相等、异常/闭包/生成器，
也没有实现origin-ID与安全别名物化。纯数值容器实验不观察新增数字身份；已有引用数值
不随意拆成inline。None在scratch用null语义代表，而生产仍用PyNone.Instance。
因此原型只能选择后续实验方向，不能直接替代生产Dynamic ABI或作为默认全项目加速承诺。

## 分阶段迁移建议

1. 已完成此矩阵，下一步选择试验分支而非立即修改MirType::Dynamic；保留当前F64与整数选择性路径。
2. 先定义FromExisting/Fresh/Materialize/Unbound与alias契约，补NaN键、默认值、闭包、异常、
   用户回调返回原盒、溢出/类型变化语义测试；身份无解前不能全动态切换。
3. 做一个明确封闭的typed调用岛或内部numeric buffer；边界次数、box次数和GC扫描一起测。
   若每轮仍跨object ABI，优先消除边界而不是为struct吞吐数字扩大错误语义。
4. 再评估typed容器值槽，保持公开操作与dict键身份/哈希契约；通过真实项目混合引用负载，
   不用纯数值数组结果外推list/dict全面改善。
5. 只有可回退的双ABI和完整身份/异常/生成器协议成立，才提新的替代ADR和广泛迁移。
   codegen引用签名、MIR验证、PIC返回/缓存、函数绑定、frame/closure/args必须同步。

逻辑union不必强制热CIL调用每次搬运物理struct：可以在MIR表示一个动态和类型，
在热局部拆为tag/ref/bits的SSA成员、在存储或冷边界才实体化。此路线比不断新增单一表达式
peephole更通用，也能避开已观察到的24B返回缓冲；但仍必须明确origin/alias与逃逸时统一
物化协议，不能用多局部表示本身假装身份问题消失。16B封闭调用岛与24B origin设计可并行
研究，先以性能/正确性门禁选边界，再谈全动态ABI。

当前推荐是“用证据挑战旧object唯一选择，但先保留多表示/边界物化”，不是断言union必快，
也不是因为身份困难就停止探索。origin-ID与安全typed容器值得独立后续实验。
