# 2026-10-31 M2.1 实现总结：动态值管线与静态特化的降级策略

- 日期：2026-10-31
- 关联里程碑 / ADR：[M2.1](../../TODO.md)、[ADR-0010](../adr/0010-dynamic-value-representation.md)

## 做了什么

### 1. 类型层：从「报错」改成「降级」

每个函数有一个 `FuncMode`：

| 情况 | 结果 |
| --- | --- |
| 标注齐全 + 所有调用点实参一致 + 体内可静态定型 | `Static`（Phase 1 的 i64/f64 直算） |
| 缺任一标注 | `Dynamic`（初始化就确定） |
| 异构赋值 / 多返回类型 / 静态可见的类型不兼容 | 检查到就降级 |
| 调用点实参与静态签名不符 | **被调函数**降级 |
| 超出 i64 的整数字面量 | 降级（需要 BigInteger） |

降级单调、用不动点迭代：每轮重新计算签名，发现新的降级来源就重跑，最多 16 轮。收敛后用最终
模式产出类型旁表。动态函数不写旁表，下游读取一律得到 `Dynamic`——这比「给每个表达式填
Dynamic」省事，也避免旁表与模式不一致。

`E0201`（缺标注）与「实参类型不符」的 `E0203` 都已取消：Python 不因标注拒绝实参。

### 2. MIR：装箱、拆箱与动态运算

新增 `MirType::Dynamic` 与四个 rvalue：`Box`、`Unbox`、`DynBinary`、`DynCompare`、
`DynUnary`、`DynTruthy`。核心约束是**每个赋值点都做类型对齐**——`assign_value()` 是唯一
写局部变量的入口，按「动态 → 静态拆箱 / 静态 → 动态装箱」补一条指令，这样 codegen 永远
看到栈类型与槽类型一致。

`for i in range(...)` 在动态函数里仍是计数循环：边界先拆箱成 i64，循环变量每轮装箱写回。
这样 `range` 不会退化成迭代器，也顺手保住了 Phase 1 的循环性能。

### 3. codegen：`object` + 统一运算 ABI

`MirType::Dynamic` → `System.Object`；装箱用 `box int64/float64/bool`（引用类型跳过），
拆箱调 `PyCast.ToInt64` 等。动态运算把操作码当立即数压栈，再调 `PyOps.Binary(int, object,
object)`——ABI 面只有三个方法，比「每个运算符一个方法」更不容易与 Rust 侧漂移。

`ClassTypeMap` 从裸 `HashMap` 改成带 `object: TypeRefIndex` 字段的结构体：`System.Object`
是外部类型引用，不能塞进用户类的 `TypeIndex` 映射里。

### 4. 验收用例

| 用例 | 覆盖 |
| --- | --- |
| `m2_1_dynamic.py` | 标注不限制实参（`twice("ha")`）、多返回类型、异构赋值、`True + 2`、`and`/`or` 返回操作数 |
| `m2_1_dynamic_flow.py` | 动态值 + for/while/条件分支/字符串拼接/`not`/幂、整除、取模、取负、abs |
| `m2_1_bigint.py` | `-2**63` 字面量、溢出升级、`10**40`、移位、负除数整除、`int("...")`、与 float 的精确比较 |

三个用例都与 CPython 逐字节一致；`m2_1_calls.py` 仍 pending（要等函数对象与容器）。

## 踩到的坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `InvalidProgramException`（无任何输出） | 比较 / `not` 在动态函数里返回了裸 `bool`，却被当成 `object` 存进局部变量 | 动态上下文里比较结果要装箱；新增 `bool_to_value()` 统一处理 |
| 直接索引 `types.bodies[fn]` 越界 | 动态函数没有旁表，`ArenaMap` 索引直接 panic | 全部改走 `TypeckResults::expr_ty` / `local_ty`，缺失即 `Dynamic` |
| 异构赋值后仍按 `Int` 编译，运行期 IL 非法 | `unify` 失败被 `let _ =` 吞掉，变量仍绑定第一次的类型 | unify 失败时 `force` 成 `Dynamic` 并标记降级 |
| `method_ref!` 里 `#type` 与 `@type` 混用编译不过 | `#` 会移动 `MethodType`，同一个类型被两个宏用时后一个报「use after move」 | 统一用 `@`（借用），只在使用处保留一个 `#` |
| `Normalize` 恒返回 BigInteger | C# 三元表达式两个分支被统一成 `BigInteger` | 改 if/else（上一轮已记录，这次在 `PyInt` 里固定下来） |

## 学到的概念

- **降级判定要单调**：允许「降级后回升」会让不动点迭代不收敛，也会让同一份代码在不同编译
  顺序下得到不同性能特征。只降不升是最省心的不变量。
- **旁表缺失 = Dynamic** 是个好用的默认值：动态函数不需要填任何类型，下游也不必到处判空。
- **装箱与拆箱必须集中在赋值点**：分散在表达式构建里很容易漏掉一条路径，而 CIL 的
  `InvalidProgramException` 不会告诉你是哪一条。
- **静态特化的溢出退路**：静态 i64 仍然 checked（`add.ovf`），要正确的大整数语义就去掉标注
  走动态路径。这是 ADR-0010「装箱 ABI + 静态特化」的直接推论，已登记进 semantics 陷阱 #4。

## 还没想明白的

- 动态函数的属性访问要等 M2.5 的普通 class；现在报 `E0303`，是明确拒绝而不是占位。
- `m2_1_calls.py` 需要函数对象、默认参数、`*args` / `**kwargs`，全部依赖 tuple / dict，
  顺序上必须排在 M2.3 之后。
- 动态算术的装箱成本仍是静态路径的约 10 倍（ADR-0010 的基准）。PIC 与拆箱优化留到 M2.9，
  先保证正确性。
