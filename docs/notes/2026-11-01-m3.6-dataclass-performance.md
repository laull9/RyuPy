# M3.6 数据类性能：正确表示后的三轮优化

日期：2026-11-01。数据位于 `tests/perf/results/m3_6/`。测量发生在未提交的 M3.6 工作树，
基线提交为 `86c4ad977a245e16748bff88ee0e1c9c64d1bff2`，不代表发布版承诺。完整语义/集成门禁由里程碑统一记录；本记录只描述性能实验及构造守卫专测。

测量平台：Linux x86_64，.NET SDK 10.0.403，Microsoft.NETCore.App 10.0.14（经
`uname -sm`、`dotnet --version`、`dotnet --list-runtimes` 确认）。这是共享 cloud executor，
不是隔离裸机；`lscpu` 的硬件探针因 `/sys` 缺失未能确定 CPU 型号，不假设固定硬件频率。
下述数据均为有噪声的有限样本，不外推为其它机器、项目或发布版本的普遍速度承诺。

## 1. 分阶段比较不能混为一谈

### 旧静态表示与正确动态表示

`static-before.json` / `dynamic-before.json`：同一 `tests/perf/dataclass_hot.py`，每进程三次
预热、七次计时取中位数。构造包含对象创建和读取/累加；字段读取包含循环和两次加法，**不是纯属性读取**。

| 工作负载 | 旧静态 CLR 表示 | 正确 PyClass/PyInstance |
| --- | ---: | ---: |
| 构造 50,000 次 | 1.25 ms | 25.62 ms |
| 字段读取循环 200,000 次 | 0.399 ms | 4.72 ms |

旧 equality 返回 0，新实现返回 50,000，不能比较其速度。静态表示还缺少类重绑定、身份和
数据类协议，不能作为无条件恢复的优化。整函数 Dynamic 同时改变算术和装箱路径，不能把
字段基准的全部差距归因为名字查找。

### 正确动态表示与缓存构造计划

`constructor-comparison.json`：每种配置独立运行三个进程，各进程仍七次采样；下表再取三个
进程中位数的中位数。`0` 为 `DOTNET_TieredCompilation=0`，`1` 为启用分层 JIT。

| 构造 50,000 次 | 优化前 | 构造计划 | 比值 |
| --- | ---: | ---: | ---: |
| 分层 JIT 开启 | 20.47 ms | 8.18 ms | 2.50× |
| 分层 JIT 关闭 | 16.56 ms | 5.17 ms | 3.20× |

计划绑定生成的 `__init__` 对象和槽索引。任何类修改后检查类版本、方法身份与 property；
只优化完整位置实参、全部参与 init 且无 factory 的字段。关键字、缺参、factory、描述符、
自定义 init 与定义时已有 post-init 均回通用路径。实例仍有独立对象与独立槽数组。

post-init 是否被调用在生成 init 时决定：之后新增的方法不应被调用；原有方法重绑定要生效，
删除要报 AttributeError。守卫专测覆盖这些规则、冻结、身份、默认值和参数错误，共五项。

### 相同优化运行时，删除无用装箱前后

`dce-comparison.json`：旧编译产物与加入 DCE 的产物复制**同一份最新运行时**，避免把运行时
改动混进编译器收益。采样策略与上组相同。

| 工作负载 | 分层 JIT | DCE 前 | DCE 后 |
| --- | --- | ---: | ---: |
| 构造 50,000 次 | 开 | 7.705 ms | 6.669 ms |
| 字段读取循环 200,000 次 | 开 | 5.874 ms | 3.420 ms |
| 构造 50,000 次 | 关 | 5.688 ms | 5.155 ms |
| 字段读取循环 200,000 次 | 关 | 5.938 ms | 4.774 ms |

仅删除全函数未读取局部的 Use/Box 到不动点；不删除调用、属性访问、拆箱、算术或可能抛错的
操作。MIR 中未使用的循环变量 `i` 的赋值/装箱消失，控制循环的原生计数器保留。
分层 JIT 的 equality 数字仍不稳定，尤其优化后有两个进程尚在较慢层级，不能宣传为等值回退
或加速；关闭分层 JIT 的原始数据亦保留供检查。所有工作负载结果校验值保持一致。

## 2. 独立分配诊断与热点归因

`diagnostics/Program.cs` 是临时诊断的可复现副本，**不是生产代码，也不是编译器反射执行路径**。
它使用 `GC.GetAllocatedBytesForCurrentThread()`。编译方法测试先调用程序集入口初始化常量/
模块，再通过反射进入 `m0_field_reads`；反射开销跨 200,000 次循环摊薄，不能省略初始化。
三个 `allocation-*.txt` 保存完整输出。以下字节数比单次纳秒计时更稳定：

| 操作 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 构造，调用方复用实参数组 | 120 B/对象 | 72 B/对象 |
| 构造，包含新实参数组和两个整数盒 | 208 B/对象 | 160 B/对象 |
| 实际编译字段循环，DCE 前后 | 47.96 B/轮 | 24.00 B/轮 |

构造少分配一个含 self 的数组（48 B），不是消除了对象身份。字段循环少分配约一个整数盒
（24 B/轮）；预热与小整数缓存使优化前平均略低于 48 B。反射诊断关闭分层 JIT，字段循环
单次为 32.14→24.08 ns/轮，结果均为 1,400,000。

独立 C# 同一委托框架下，PIC 两字段纯读取约 19.5–21.3 ns、0 B；通用 GetAttr 两读取
约 97–99 ns、0 B。数组基线 13–22 ns 波动较大，不宜作精确差值。只执行动态数字累加约
28.7–38.2 ns、24 B，PIC 读取加累加约 28.4–36.3 ns、24 B。以上是单次诊断区间，不是
严谨置信区间，不能相减推算独立组件的精确成本。

**结论**：已有 shaped slots 与 PIC 确实在工作。剩余确定分配是每轮累加器的新盒；`x+y=7`
命中小整数缓存。不要把全部差距误诊成四路 PIC 扫描，也不要宣称本轮已追平静态表示。

## 3. 复现

先按项目流程构建 Release 运行时与 CLI，然后：

```bash
python3 tests/measure_dataclass.py --cli target/release/ryupy \
  --runtime runtime/RyuPy.Runtime/bin/Release/net10.0 \
  --output /tmp/ryupy-dataclass-measure

dotnet build tests/perf/results/m3_6/diagnostics/alloc.csproj -c Release
DOTNET_TieredCompilation=0 dotnet \
  tests/perf/results/m3_6/diagnostics/bin/Release/net10.0/alloc.dll \
  /tmp/ryupy-dataclass-measure/dataclass_hot.dll
```

三进程、两种分层 JIT 配置的比较脚本也已归档；两目录须先准备为同负载、相同运行时：

```bash
python3 tests/perf/results/m3_6/compare.py before=/tmp/before after=/tmp/after \
  --output /tmp/comparison.json
```

脚本检查返回校验值与语义首行相同，不允许把旧错误 equality 混入等价比较。

不传程序集参数时只运行独立运行时诊断。对比历史运行时须将 harness 产物复制到独立目录再
替换其中的 Runtime DLL，不覆盖生产输出；对比 DCE 必须让两份编译产物使用同一运行时。
分层 JIT 开/关分开报告，不混取最小数；避免构建与测试并行污染测量。原始运行时/CLI 二进制
不提交，因此历史重现需对应源码快照；本目录保留的是数据与实验实现，不是自包含二进制包。

## 4. 下一优化边界

1. 探索非逃逸数值局部的带守卫表示：实际类型为 long 才走 checked 加法，溢出升级 BigInteger，
   遇其它类型回原动态协议；不能因注解写 int 就拒绝或错误拆箱其它值。
2. 只有不可观察时延后装箱。值经返回、调用、闭包、容器或身份比较暴露前须物化；同一值重复
   暴露应复用同一盒，避免改变身份/别名。需独立 MIR 设计和边界测试，不能凭基准单独硬编码。
3. PIC 单态热路与冷路径拆分可单独实验，但须保留版本、描述符优先级、删除/遮蔽、四路多态和
   容量上限；应先用纯读取诊断证明收益，再讨论代码复杂度。
4. 关键字绑定计划、带默认值构造可后续扩大；工厂的调用次数、顺序及返回对象新鲜度不可牺牲。

验收至少包含 BigInteger 边界、循环中值类型变化、类/描述符替换、getter与比较副作用、异常
路径、身份/别名、冻结与默认工厂，并同时保留固定项目回归。不得为性能改写预期结果。

## 5. 继续实验：一次调用一个累加槽（运行时初证）

为避免未经实证停留在规划，新增内部 `PyNumericAccumulator.Create/Add/Value` 原型：一次函数
调用一个 holder，实际 long 结果存原生字段，观察时才缓存装箱；其它类型与溢出执行完整
`+=` 动态协议。初始值和用户运算方法返回对象保留原身份，异常前不更新累加状态。

五项运行时测试通过，覆盖双向整数溢出及回落、bool/float、错误后状态、反射/原地方法、原始
及缓存盒身份。MIR 只允许严格证明无循环内观察/逃逸的局部；编译器接入与最终门禁另行验收，
不能把此处运行时初证误称为完整编译器优化已完成。

`accumulator-diagnostics/` 保存该实验 harness，`accumulator-runtime.txt` 保存完整输出。
一次关闭分层 JIT 的运行，PIC 读取加动态累加为 26.99 ns/轮、24 B/轮；相同读取加 holder
为 10.44 ns/轮、0 B/轮。一次 holder 的分配发生在计时循环外，应计入函数调用成本，不能
宣传整个函数零分配。最终 14,070,000 包含 10,000 次预热和 2,000,000 次计时，每次加 7。
这些是单次诊断，不是最终同负载、多进程编译产物 A/B；但证明方案没有逐轮新 wrapper，
足以支持继续做受守卫的编译器实验，而不是恢复错误的固定 i64 字段表示。

## 6. 累加槽编译器接入后的最终隔离比较

Rust pass 现在已接入并验过真实 e2e：只有无异常区、非闭包/生成器、严格单入口自然循环，
且累加局部循环内唯一读写是末尾的 `+=` 才改写。preheader 创建 holder，body 调用 Add，
唯一 exit 物化回原局部。循环中观察或额外赋值、复杂控制流均不匹配；无类型注解假设。

`accumulator-comparison.json` 用同一份最终运行时隔离比较 DCE 产物与加入累加槽的产物，
仍为三个进程各七次取中位、再跨进程取中位。最终集成运行时 297 项测试通过（主线程记录
`/tmp/ryupy-m3_6-runtime-with-accumulator.log`）。最终 `make runtime` / `make check` 与固定项目
回归整体退出码均为 0：C# 297 项通过，e2e 122 项通过、16 项跳过，Python 基线 134 项
通过。固定项目集仍为 0/20 原生通过、20 项 unsupported；性能改善不计作项目兼容率提升。

| 工作负载 | 分层 JIT | DCE 版本 | DCE + 累加槽 |
| --- | --- | ---: | ---: |
| 构造 50,000 次 | 开 | 6.622 ms | 6.427 ms |
| 字段读取循环 200,000 次 | 开 | 3.201 ms | 2.161 ms |
| 构造 50,000 次 | 关 | 5.607 ms | 3.991 ms |
| 字段读取循环 200,000 次 | 关 | 3.993 ms | 2.508 ms |

读字段负载获得约 1.48× / 1.59× 的**增量**改善；默认分层 JIT 构造增益很小，不能套用
关闭分层 JIT 的 1.40× 宣传默认配置。equality 没有被候选匹配，本轮不宣称优化它。

`compiled-allocation-{dce,accumulator}.txt` 保存实际编译方法的独立分配诊断：五次调用，
每次 200,000 轮，分配总量从 **23,995,720 B 降到 360 B**，结果都为 **1,400,000**。
360 B 包含计时/反射固定开销，平均约 72 B/函数调用，不是函数零分配；holder 与最终返回
盒仍存在。逐轮分配消失，不能据显示四舍五入为 0.00 B/轮便宣称整个对象模型无分配。
该次关闭分层 JIT 的直接调用计时为 29.65→16.07 ns/轮，正式性能数字以上述多进程表为准。

本轮依次实证并实现缓存构造计划、无用装箱消除、带守卫的累加槽，而非只接受正确但极慢的
动态路径。仍未追平旧静态 CLR 字段表示，也未恢复其错误的 identity/eq/类修改语义。不同
轮次受 JIT 和主机状态影响，不能把各轮倍率相乘。后续如优化 PIC 冷热拆分或扩大候选，仍需
用纯读取与同负载结果分别验收，保留全部守卫及动态回退。
