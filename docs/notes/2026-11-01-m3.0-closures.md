# M3.0：闭包、lambda 与 nonlocal

- 日期：2026-11-01
- 关联：[ADR-0015](../adr/0015-shared-closure-cells.md)

## 一条闭包如何运行

`counter()` 为 `value` 创建 cell，把 0 写进去。执行内部 `def add` 和 `def read` 时分别创建
函数对象，两份环境数组都引用同一个 cell。外层函数返回后，两个函数对象继续持有 cell；
`add` 写入的值会被 `read` 读到。再次调用 `counter()` 会创建另一套 cell。

编译时，HIR 先建立作用域树，沿父链区分局部、模块变量与 free。中间函数即使没有读取某个
名字，也要转发更深层闭包所需的 cell。MIR 把这些关系写成 `CellNew`、`CellGet`、
`CellGetFree`、`CellSet` 和 `MakeFunction`；CIL 只负责数组、委托、隐藏环境参数与方法调用。

thunk 现在首先接收函数实例，从中取默认值与环境。签名仍按源码定义共享。原有 CIL 快照
因此会出现统一变化：thunk 多一个 PyFunction 参数，实参下标后移，默认值改从实例读取，
函数构造器多一个环境参数。原有 Python 参数数量与调用行为保持一致。

## 收尾时修正的问题

分支和循环内的 def 一度被直接追加到函数根语句列表。这样会绕过条件、提前创建函数，
循环中的默认值也会读到错误时刻的值。现在 def 返回普通语句节点，由所在语句块保留位置。

默认值表达式属于外层作用域。只扫描嵌套函数体会漏掉 `def inner(x=seed)` 对 seed 的读取，
默认值里的 lambda 也会漏登记。def 和 lambda 现在共用发现流程，默认值留在当前收集器中。
参数默认值数组按位置参数、星号参数、仅关键字参数、双星号参数排列，避免有 `*args` 时错位。

`nonlocal` 中间层的赋值不能变成本层绑定；外层的 global 则必须截断继续查找。
多层转发、global 屏障和互相递归都有差分用例。空 cell 按读取作用域抛异常：当前函数抛
UnboundLocalError，自由变量抛 NameError。仅比较消息会漏掉两者的继承关系，所以测试先捕获
UnboundLocalError，再捕获 NameError。

AST 节点查找改用完整 visitor，lambda 放在 assert、raise、f-string 等位置也能找到。
声明检查单独拒绝参数冲突、global / nonlocal 冲突和先用后声明。诊断快照统一源码路径，
避免依赖本机临时目录。

## 验收范围

`m3_0_closures.py` 保留共享计数器、模块循环 late binding 与默认参数捕获。
`m3_0_scope_edges.py` 补充函数内循环捕获、多个工厂实例、互相递归、三层 lambda、
定义期默认值、可变默认值身份、分支内同名 def、嵌套 global、正常 except 退出的 cell 清理、
外层返回后调用以及空 cell 的异常类型。`m3_0_exception_cells.py` 另测 return、break、continue、再抛异常和 nonlocal 异常绑定的清理，清理复用 finally 展开通道。运行时另有两个 cell 单测。

HIR / types / MIR / CIL 与八组非法 nonlocal 声明都有快照。
`make check` 通过：CPython 基线 70 项，运行时 97 项，Rust 单元与快照通过，
正式 e2e 55 项通过、19 项仍按原来的后续里程碑保持 pending。
固定项目集重跑仍为 0/20，未更改分母；各项目的首个阻塞见 compatibility.md。

## 闭包调用成本

输入为 `tests/benchmarks/closures.py`：100 万次捕获参数的加法调用、100 万次 nonlocal
计数调用，再对 5 万个元组用 lambda key 排序。每次运行都核对 CPython stdout。

2026-11-01，Apple M5、macOS arm64，CPython 3.12.13、.NET SDK 10.0.403，Release CLI。
一次热身后计时九次，每次启动新进程；下表取中位数。进程内执行时间仍含这次进程的 JIT，
不能据此宣称测到了独立稳态吞吐。

| 指标 | CPython | RyuPy |
| --- | ---: | ---: |
| 墙钟时间 | 97.6 ms | 138 ms |
| RyuPy 入口执行时间 | 未作此项对比 | 117 ms |
| 峰值内存 | 23.5 MiB | 58.0 MiB |
| 托管分配量 | 未测量 | 104.0 MiB |
| GC 0 / 1 / 2 次数 | 未作此项对比 | 12 / 1 / 1 |
| GC 暂停 | 未测量 | 3.0 ms |
| JIT 时间 | 不适用 | 19 ms，114 个方法 |

本轮 CPython / RyuPy 为 0.71 倍，RyuPy 更慢；墙钟波动 25%，只作为当前成本记录。
首次五次计时得到 0.78 倍、波动 18%，也未显示速度优势。已执行与 M2.12 基线的对比，
旧基线没有闭包通过项，因此没有可计算的前后提升。九次结果保存为构建目录下
`bench/results/m3.0.json`，后续可用 `make bench-compare BENCH=closures NAME=m3.0` 对比。

签名按源码函数数量增长，不按调用次数积累；cell、环境和默认值随可达函数存活。
互相递归形成的环交给 CLR GC。这个基准覆盖百万次调用和多轮 GC，没有验证无限期运行。
