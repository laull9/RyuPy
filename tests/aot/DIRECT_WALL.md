# 无统计污染的同源直接 wall 对照

目的：修正旧基线 CPython 使用统计外壳而产品使用各自统计路径造成的启动比较不公平。
旧 run 43596268398 的约20GB str_concat末次托管累计分配只作热点线索，不是峰值内存。
本切仅测试设施，不修改语言语义、provider、onefile、Python绑定或被测负载。

## 冻结输入与工具

沿用 `hello.py`、`calls.py`、`str_concat.py` 原源码/循环，干净完整提交固定输入。
Linux x64，GitHub ubuntu-24.04共享runner；Python 3.12.13，独立SDK 10.0.403。
记录完整commit、CPU/平台、解释器及dotnet路径/rustc版本；检查实际SDK和AOT清单。
每源仅构建一次AOT，JIT运行该次发布的同一managed DLL，所有构建在计时前完成。

## 直接wall阶段

- CPython：`python -B 原源码.py`；无runpy、gc/json外壳，无统计文件参数。
- JIT：已核dotnet＋同次managed DLL；AOT：直接原生可执行文件。
- 三臂均不设置RYUPY_STATS；剥离实验/Python注入环境，hash seed=0，输出原字节保留。
- 每负载每臂一次预运行，CP直接输出成为本轮oracle。之后固定六轮，每负载三臂六个
  全排列各一次，每个位置各出现两次；负载顺序随轮次轮转。无自适应追加或择优删除。
- 总计63次无统计应用进程，54个计时样本。每次都是新进程，不清OS文件缓存；预运行
  不代表进程内暖稳态，也不消除共享runner干扰。轮转只降低顺序偏差，不保证独立同分布。
- 复用perf_runner的wait4与进程组限时；每应用120秒，编译300秒，整组2400秒。
  非零退出、超时、泄漏子进程、双流不符、坏样本或统计污染都失败，不静默跳过。

## 诊断阶段

全部直接wall结束后，另起每负载每臂一次诊断，共9次：CP使用既有统计外壳，JIT/AOT
设置RYUPY_STATS。诊断统计严格解析，仍对照同次oracle。诊断wall/Main绝不进入直接wall
汇总，其进程原始status时间仅作取证，不是可比较性能指标。托管累计分配、heap、GC与
操作系统峰值RSS不同，不能混称内存占用；AOT JIT统计不用于计算加速。

## 结果与限制

`wall.json`仅含54个直接wall样本与每负载每臂的中位/min/max；`diagnostics.json`仅含
单独诊断统计和证据位置；`run.json`登记状态、源码/工具、实际产物/构建时间和口径。
每个进程的命令、双流、退出/超时/RSS状态均保存在仓库外工件；直接wall环境中若出现统计
文件或统计摘要则拒绝。失败也保留已产生原始证据，不添加生成golden或原始数据到Git。

只报告这一提交/机器/负载的观测；不是暖吞吐、Nuitka对照、优化前后效果或普适加速承诺。
JIT/AOT仍包含产品自带的默认启动检查，它属于产品成本，不是测试附加统计。
原位/搬迁正确性门独立保留，不混入计时样本。首次真实运行待CI，轻测不能代替实际数据。

直接wall包含进程启动、输出及固定外部测量开销，不称纯执行吞吐。wait4的RSS可能包含
fork时继承的父进程内存高水位或平台测量下限；本轮仅留原值供诊断，不能据此宣称内存优势。
