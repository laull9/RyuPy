# 有界交互标准输入诊断

这是根据旧聊天摘要重建的猜数候选、插桩候选及输入/分支隔离程序，**不是用户原始1.py**。
用户原文件/机器版本尚待核实，不把本诊断通过或失败等同原问题已经修复。

旧产品基线为main `457886017cd4d32911a09b09307d07c327b87192`；当前workflow固定
独立CR修复 `027ed394cf388218ac48268025083c7ae762afcb`，独立重建CLI/runtime；
实际调用`ryupy run`。使用CPython3.12.13，记录OS/架构/.NET/产品SHA及PTY初始termios，
不修改终端设置。macos-latest runner不代表用户具体硬件或Terminal环境。

固定两输入序列、三候选源，pipe与逐prompt PTY；PTY分立即/100ms延迟及LF/CR。
最多30对子/60应用进程；每进程15秒、总120秒，首基础错误或超时停止并留原始证据，
不自动重跑或谎称完成全部矩阵。独立进程组覆盖CLI派生的dotnet，超时清理且回收。

原stdin/双流或PTY合流、退出码、时间设置均进CI artifact（14天），不提交raw logs到Git。
`raw_equal`与去固定提示/单字符echo后的`behavior_equal`分开：后者仅诊断程序输出，
不能冒称原始终端字节相同。普通退出必须0；最终完整矩阵强锁30对子。

当前Linux已见：LF下控制流与CP一致；立即投喂有首次额外echo，延迟后消失。
CR下第二次输入后超时，延迟CR及独立input分支程序亦复现；这是相关读取缺陷证据，
**尚未证明就是用户macOS错判的根因**。旧macOS CI41413991719也实际CR超时。修复后的Linux同30对子/60应用进程已完整通过
控制流对照，12个立即投喂PTY仍仅有首字符额外echo，不称raw全一致。修后macOS待CI，
此诊断工具提交不修改生产；生产修复保持独立分支。
